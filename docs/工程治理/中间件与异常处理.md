# 中间件与异常处理

## 1. 概览

中间件与异常处理承担系统**全局横切关注点**：请求追踪、耗时统计、跨域、日志与统一错误格式。核心代码：

| 内容 | 状态 | 位置 |
| --- | --- | --- |
| 请求追踪（X-Request-ID / trace_id） | ✅ | `backend/src/utils/trace_id.py`、`ContextMiddleware` |
| 耗时统计 | ✅ | `backend/src/middleware/access_middleware.py` + Prometheus 指标 |
| CORS | ✅ | `register_middleware` + 异常场景补头 |
| 全局异常处理器（统一 JSON） | ✅ | `backend/src/common/exception/exception_handler.py` |
| 日志中间件（访问 + 操作） | ✅ | `access_middleware.py`、`logs_middleware.py` |
| 日志配置（loguru + request_id） | ✅ | `backend/src/common/log.py` |

## 2. 请求追踪（X-Request-ID）

### 2.1 链路

```text
请求头 X-Request-ID（可选，validate=True 校验）
  → ContextMiddleware 插件写入 ctx（默认 RequestIdPlugin / Grafana 开启时 OtelTraceIdPlugin）
  → ctx 持有 trace_id
  → 日志：request_id_filter 截断写入每条日志（TRACE_ID_LOG_LENGTH=32）
  → 响应：错误响应体携带 trace_id；CORS expose X-Request-ID 供前端读取
```

- 配置：`TRACE_ID_REQUEST_HEADER_KEY = 'X-Request-ID'`，`TRACE_ID_LOG_DEFAULT_VALUE = '-'`
- 默认插件 `RequestIdPlugin(validate=True)`：优先沿用请求头传入的 `X-Request-ID`（非法 UUID 则重新生成），保证**跨服务调用可串起全链路**
- 启用监控时切换 `OtelTraceIdPlugin`：trace_id 取自 OpenTelemetry span，与 Grafana/Tempo 对齐
- 日志关联：`common/log.py` 的 `request_id_filter` 将 `request_id` 注入每条 loguru 记录，错误响应体亦带 `trace_id`，日志 ↔ 响应可互查

### 2.2 追踪 ID 规范

| 场景 | 取值 |
| --- | --- |
| 请求头 | `X-Request-ID`（客户端可传，网关建议统一覆盖） |
| 日志字段 | `request_id`（截断 32 位） |
| 错误响应 | `trace_id` 字段（与日志一致） |
| 操作日志 | `sys_opera_log.trace_id` 落库 |

## 3. 耗时统计

`AccessMiddleware` 全量统计：

- **精确计时**：`time.perf_counter()` 记录 `ctx.perf_time`，`timezone.now()` 记录 `ctx.start_time`（供操作日志取业务时间）
- **访问日志**：`--> 请求开始` / `<-- 请求结束`（debug），汇总行 `IP | METHOD | CODE | PATH | elapsed`（info）
- **指标**（`GRAFANA_METRICS_ENABLE` 时，仅统计 `/api/v1/*`）：
  - `fastapi_request_in_progress`（当前并发 gauge）
  - `fastapi_request_total` / `fastapi_response_total`（按 method/path/status 计数）
  - `fastapi_request_cost_time`（耗时直方图，携带 trace_id exemplar）
  - `fastapi_exception_total`（按异常类型计数）
- **操作日志耗时**：`OperaLogMiddleware` 复用 `ctx.perf_time` 计算 `cost_time`（ms）落库 `sys_opera_log`

## 4. CORS

- 开关：`MIDDLEWARE_CORS=True`；配置 `CORS_ALLOWED_ORIGINS`（默认 `http://127.0.0.1`、`http://localhost:5173`）
- 参数：`allow_credentials=True`、`allow_methods=['*']`、`allow_headers=['*']`、`expose_headers=['X-Request-ID']`
- **异常场景补头**：500 类异常可能绕过 CORS 中间件响应，`cors_custom_code_500_exception_handler` 手动按 `Origin` 校验并补 `Access-Control-Allow-Origin`（含 `Vary: Origin`）
- 生产建议：显式声明前端域名列表，避免通配符 + credentials 组合

## 5. 日志中间件

### 5.1 访问日志（`AccessMiddleware`）

记录请求开始/结束、路径、耗时；异常时按 ctx 中的异常信息归类计数（见第 6 节异常上下文）。

### 5.2 操作日志（`OperaLogMiddleware`）

- 仅统计 `/api/v1/*`（排除 `OPERA_LOG_PATH_EXCLUDE`），GET/OPTIONS 不落库
- 字段：`trace_id / username / method / title(路由summary) / path / ip / 属地 / user_agent / os / browser / device / args / status / code / msg / cost_time / opera_time`
- 请求参数 `desensitization` 脱敏（密码等敏感字段）
- **异步落库**：写入 `asyncio.Queue`（`OPERA_LOG_QUEUE_MAXSIZE`），`batch_consume` 批量消费（`backend/src/common/queue.py`），lifespan 启动消费任务、关闭时取消

### 5.3 日志配置（`common/log.py`）

- loguru 驱动，`InterceptHandler` 将标准库日志重定向到 loguru
- stdout 控制台 + `LOG_DIR` 下 access/error 文件（`set_custom_logfile`）
- `request_id_filter` 注入 `request_id`；`sqlalchemy echo` 输出单行化

## 6. 全局异常处理器

### 6.1 需要捕获的异常清单

| 异常 | 来源 | 处理器 | 状态码 | 响应 |
| --- | --- | --- | --- | --- |
| `HTTPException`（含 `TokenError` 等 `HTTPError`） | FastAPI/认证 | `http_exception_handler` | 原码（非法回落 400） | dev 显示 detail，prod 脱敏为 400 通用文案 |
| `RequestValidationError` | FastAPI 参数校验 | `_validation_exception_handler` | 422 | 字段级错误、i18n 文案，dev 附 `data.errors` |
| `ValidationError` | Pydantic 校验 | 同上 | 422 | 同上 |
| `AssertionError` | 代码断言 | `assertion_error_handler` | 500 | dev 显示断言信息，prod 通用 |
| `BaseExceptionError`（业务异常） | service/业务代码 | `custom_exception_handler` | 自定义 code | `{code, msg, data}` + trace_id |
| `Exception`（未知异常） | 任意未捕获 | `all_unknown_exception_handler` | 500 | dev 显示原始消息，prod 通用 |
| 500 跨域场景 | — | `cors_custom_code_500_exception_handler` | 按异常 | 补 CORS 头 |

### 6.2 业务异常体系（`backend/src/common/exception/errors.py`）

`BaseExceptionError` 基类：`code / msg / data / background`（支持 Starlette `BackgroundTask`，如登录失败写日志）。

| 异常 | 默认状态码 | 典型场景 |
| --- | --- | --- |
| `RequestError` | 400 | 参数业务校验不通过 |
| `TokenError`（HTTPError） | 401 | JWT 无效/过期 |
| `ForbiddenError` | 403 | 演示模式拦截、OAuth2 非法 state |
| `AuthorizationError` | 403 | 权限不足、账号锁定 |
| `NotFoundError` | 404 | 资源不存在 |
| `ConflictError` | 409 | 唯一键冲突（用户名/编码重复） |
| `ServerError` | 500 | 服务端错误（如雪花未初始化） |
| `GatewayError` | 502 | 网关/依赖服务异常 |
| `CustomError` | 自定义（如 40001 验证码错误） | 业务自定义错误码 |

### 6.3 统一 JSON 错误格式

所有异常出口统一为：

```json
{
  "code": 401,
  "msg": "Token 无效",
  "data": null,
  "trace_id": "3f2a..."
}
```

- **code**：业务/HTTP 状态码（与 HTTP status 一致，`_get_exception_code` 校验合法性）
- **msg**：i18n 文案（`t()` 按语言切换）
- **data**：业务附加数据（422 的字段明细仅 dev）
- **trace_id**：与日志 `request_id` 一致的追踪 ID
- **dev/prod 差异**：dev 暴露 detail/原始异常/字段明细，prod 一律脱敏为通用文案，防信息泄露

### 6.4 异常与中间件的联动

- 各 handler 将异常内容写入 `ctx.__request_*_exception__`，`AccessMiddleware` / `OperaLogMiddleware` 从中取 code/msg 完成指标计数与操作日志状态标记，**保证日志与响应一致**
- `background` 任务在响应后执行（如登录失败日志），不阻塞请求

## 7. 覆盖情况结论

| 用户框定内容 | 是否已做 | 说明 |
| --- | --- | --- |
| 请求 ID（X-Request-ID） | ✅ | 插件生成/校验 + 日志注入 + 错误响应透出 |
| 耗时统计 | ✅ | perf_counter 精确计时 + Prometheus 直方图 + 操作日志 cost_time |
| CORS | ✅ | 中间件 + 500 异常场景补头 + expose X-Request-ID |
| 全局异常处理器 | ✅ | 7 类处理器 + 统一 JSON 格式（code/msg/data/trace_id） |
| 日志中间件 | ✅ | 访问日志 + 操作日志（脱敏 + 异步批量落库） |

## 8. 已知缺口

- **X-Request-ID 可伪造**：`validate=True` 仅校验格式，生产建议网关统一生成/覆盖，业务侧信任传入 ID
- **中间件基于 `BaseHTTPMiddleware`**：7 层栈存在额外调度开销，高并发压测后可评估合并或改用纯 ASGI 中间件
- **操作日志队列内存态**：进程重启丢失未落库日志；如需强一致需引入消息队列（见 [消息队列设计](消息队列设计.md)）
- **422 明细仅 dev 暴露**：生产定位参数错误需依赖日志（`data.errors` 不返回）
- 参数脱敏依赖 `desensitization` 名单维护，新增敏感字段需同步登记
