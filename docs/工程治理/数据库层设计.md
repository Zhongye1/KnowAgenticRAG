# 数据库层设计（持久化基础）

## 1. 概览

数据库层是业务逻辑与认证体系的持久化基础，统一位于 `backend/src/database/` 与 `backend/src/common/model.py`：

| 内容 | 状态 | 位置 |
| --- | --- | --- |
| 连接引擎（`create_async_engine`） | ✅ 已实现 | `backend/src/database/db.py` |
| 会话工厂（`async_sessionmaker`） | ✅ 已实现（支持多数据源） | `backend/src/database/db.py` |
| ORM 模型（SQLAlchemy 2.0，未用 SQLModel） | ✅ 已实现 | `backend/src/common/model.py` + `app/*/model/` |
| Alembic 迁移脚本 | ⚠️ 占位（未上线，不生成版本脚本） | `backend/src/alembic/` |
| `get_db()` 依赖注入 | ✅ 已实现（含事务变体） | `backend/src/database/db.py` |
| 建表 / 初始化 | ✅ `create_all` + `task backend:init-db` | `backend/src/core/register.py`、`backend/Taskfile.yml` |

技术选型：

- **ORM**：SQLAlchemy 2.0 异步风格（`AsyncAttrs` + `DeclarativeBase` + `MappedAsDataclass`），**没有使用 SQLModel**
- **驱动**：MySQL → `mysql+asyncmy`，PostgreSQL → `postgresql+asyncpg`（由 `DATABASE_TYPE` 决定）
- **CRUD 增强**：`sqlalchemy-crud-plus`（`CRUDPlus`），各服务层基于会话工厂封装 DAO

## 2. 连接引擎与会话工厂

### 2.1 URL 组装

`get_database_url()`（`backend/src/database/db.py:17`）：

- 由 `DATABASE_HOST/PORT/USER/PASSWORD/SCHEMA` 字段组装，不依赖字符串拼接
- `DATABASE_SCHEMA` 默认 `ragf`；`unittest=True` 时自动切换为 `ragf_test`
- MySQL 追加 `charset=utf8mb4`（`DATABASE_CHARSET`）
- `DATABASE_SOURCES` 支持配置额外数据源（dict，JSON 形式），与默认源并存

### 2.2 引擎池参数

`create_database_async_engine()`（`backend/src/database/db.py:49`）固定参数，面向中等并发：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `pool_size` | 10 | 池内常驻连接数 |
| `max_overflow` | 20 | 峰值可超出的连接数 |
| `pool_timeout` | 30s | 获取连接超时 |
| `pool_recycle` | 3600s | 连接回收周期 |
| `pool_pre_ping` | True | 取连接前探活，避免拿到失效连接 |
| `pool_use_lifo` | False | 默认队列策略 |

> 代码中存在 TODO：连接池指标监控尚未接入（`db.py` 顶部注释）。

### 2.3 多数据源会话工厂

`DatabaseAsyncSessionMaker`（`backend/src/database/db.py:79`）：

- 按数据源名选择 `async_sessionmaker`，`default` 为必填源，缺失直接 `ValueError`
- `__call__(source='default')`：创建普通会话
- `begin(source='default')`：创建会话并开启事务，退出时自动提交/回滚
- 每个源统一 `autoflush=False, expire_on_commit=False`

模块级单例（`db.py:166` 起）：

```python
async_engine = create_database_async_engine(get_database_url())
async_db_session = create_database_async_session(async_engine, source_binds=...)
```

- `get_database_engines()`：返回全部引擎（默认 + `DATABASE_SOURCES`）
- `dispose_database()`：lifespan 关闭阶段释放所有连接池

### 2.4 生命周期管理（lifespan）

应用生命周期由 `LifespanManager`（`backend/src/common/lifespan.py`）统一编排，在 `register_app` 中以 `lifespan=lifespan_manager.build()` 挂载到 FastAPI；数据库相关初始化注册在 `backend/src/core/register.py` 的 `register_init`（`core` 阶段）。

**阶段模型**：`LifespanStage` 枚举 `core(0) / plugin(1) / tail(2)`，各 hook 用 `AsyncExitStack` 组合，**退出时逆序执行**（后注册先关闭），保证关闭顺序与依赖方向一致。

**启动（core 阶段，按序）**：

| 顺序 | 动作 | 说明 |
| --- | --- | --- |
| 1 | `await create_tables()` | 幂等建表（`MappedBase.metadata.create_all`），先于业务请求可用 |
| 2 | `await redis_client.init()` | Redis 连通性检查，失败直接 `sys.exit()` |
| 3 | `await snowflake.init()` | 雪花算法初始化：环境变量固定节点或 Redis 动态分配，主键生成依赖此项 |
| 4 | 启动 `OperaLogMiddleware.consumer()` | 操作日志异步队列任务 |
| 5 | `cache_pubsub_manager.start_listener()` | 缓存 Pub/Sub 监听器 |

**关闭（finally，逆序）**：

| 顺序 | 动作 | 说明 |
| --- | --- | --- |
| 1 | `stop_listener()` | 停止缓存 Pub/Sub |
| 2 | 取消操作日志任务 | `task.cancel()` 并等待清理 |
| 3 | `await snowflake.shutdown()` | 释放 Redis 分配的雪花节点 |
| 4 | `await redis_client.aclose()` | 关闭 Redis 连接 |
| 5 | `await dispose_database()` | **释放全部数据源连接池**（默认源 + `DATABASE_SOURCES`） |

**运行期（请求级）**：每个请求通过 `get_db` / `get_db_transaction` 的 `async with` 获取会话，请求结束自动提交/回滚并归还连接池（见第 5 章），与进程级生命周期互补。

**进程外（Celery worker / beat）**：不走 FastAPI lifespan。Celery 使用独立同步引擎（`db+postgresql+psycopg` / `db+mysql+pymysql`，见 `backend/src/app/task/celery.py`）作为结果后端，`DatabaseScheduler` / 结果表由 `DatabaseBackend`（`backend/src/app/task/database.py`）按 `database_create_tables_at_setup` 自动建表，与 Web 进程的 `async_engine` 互不影响；多进程部署时各进程持有独立连接池，需按进程数评估数据库最大连接数。

## 3. ORM 模型基座

### 3.1 基类体系（`backend/src/common/model.py`）

| 基类 | 继承 | 职责 |
| --- | --- | --- |
| `MappedBase` | `AsyncAttrs, DeclarativeBase` | 声明式基类；`__tablename__` 默认类名小写；`__table_args__` 默认表注释取 docstring |
| `DataClassBase` | `MappedAsDataclass, MappedBase` | 原生 dataclass 集成 |
| `Base` | `DataClassBase + DateTimeMixin + LogicalDeleteMixin` | 业务表通用基座（审计时间 + 逻辑删除） |

Mixin：

- `UserMixin`：`created_by` / `updated_by` 审计字段
- `DateTimeMixin`：`created_time` / `updated_time`（`TimeZone` 类型，默认 `timezone.now`）
- `LogicalDeleteMixin`：`deleted`（0 否 / id 是，带 `server_default='0'`）/ `deleted_time`

### 3.2 主键与类型兼容

- `id_key`：雪花算法 `BigInteger` 主键（`primary_key + unique + index`，`default=snowflake.generate`），见 `common/model.py:25`
- `UniversalText`：MySQL `LONGTEXT` / PostgreSQL `Text` 自动切换
- `TimeZone`：`DateTime(timezone=True)`，绑定/读取时自动补齐时区
- `uuid4_str()`：UUID 类型跨库兼容方案

> 注意点：`id_key` 固定使用雪花算法生成主键；`DATABASE_PK_MODE`（默认 `autoincrement`）只影响 Pydantic 序列化（id 是否转字符串）与代码生成模板，不改变主键生成方式。

### 3.3 模型注册机制

- 各模块 `model/__init__.py` 聚合导出（如 `backend/src/app/admin/model/__init__.py`）
- `get_all_models()`（`backend/src/utils/dynamic_import.py`）动态扫描 `app/*/model` 与插件模型，供权限校验等使用
- 实测：全量导入后 `MappedBase.metadata` 注册 **22 个模型类 / 23 张表**（含 `sys_user`、`sys_role`、`sys_menu`、`task_result` 等）

模型示例（`backend/src/app/admin/model/data_rule.py`）：

```python
class DataRule(Base):
    """数据规则表"""

    __tablename__ = 'sys_data_rule'
    __table_args__ = (
        sa.UniqueConstraint('name', 'deleted', name='uk_sys_data_rule_name_deleted'),
        {'comment': '数据规则表'},
    )

    id: Mapped[id_key] = mapped_column(init=False)
    name: Mapped[str] = mapped_column(sa.String(512), comment='名称')
    ...
```

## 4. Alembic 迁移

### 4.1 现状

- `backend/src/alembic.ini`（`[tool.alembic]` 配置在 `backend/pyproject.toml`，`script_location` 指向 `src/alembic`）
- `backend/src/alembic/env.py`：异步迁移，`target_metadata = MappedBase.metadata`，开启 `compare_type` / `compare_server_default`，无变更时不生成空迁移
- `script.py.mako` 模板就绪；`versions/` 为**占位目录**（含占位说明文件），`env.py` 运行时会自动创建

### 4.2 当前策略：占位（项目未上线）

- **有意不做真实迁移版本**：项目未上线，模型结构仍在快速迭代，此时维护迁移脚本收益低、维护成本高
- 建表统一由 lifespan 启动时的 `create_all` 负责（幂等），`task backend:init-db` 提供手动初始化入口（建表 + Redis 连通性检查）
- `versions/` 仅保留占位说明，标识「迁移尚未启用」，避免误认为已有版本管理

**上线前置动作（届时再启用，当前不做）**：

1. 生成首个基线：`alembic revision --autogenerate -m "init"`（对既有库用 `alembic stamp head` 打基线，避免重复建表）
2. 部署流程切换为 `alembic upgrade head`，并评估是否停用启动时 `create_all`

> 迁移命令依赖 `backend/src/.env`（见 [环境变量](环境变量.md)）；相关命令示例保留在 `backend/src/alembic/versions/README.md`。

## 5. get_db 依赖注入

### 5.1 会话注入

`backend/src/database/db.py`：

```python
async def get_db() -> AsyncGenerator[AsyncSession, None]:
    """获取默认数据源会话"""
    async with async_db_session() as session:
        yield session

async def get_db_transaction() -> AsyncGenerator[AsyncSession, None]:
    """获取默认数据源事务会话"""
    async with async_db_session.begin() as session:
        yield session

# Session Annotated
type CurrentSession = Annotated[AsyncSession, Depends(get_db)]
type CurrentSessionTransaction = Annotated[AsyncSession, Depends(get_db_transaction)]
```

API 中使用（`backend/src/app/admin/api/v1/auth/auth.py`）：

```python
async def refresh_token(db: CurrentSession, request: Request, ...) -> ...:
    ...
```

- `CurrentSession`：读写单条/查询场景
- `CurrentSessionTransaction`：需要显式事务边界的场景（登录、写操作聚合）

### 5.2 测试隔离

`backend/src/tests/utils/db.py`：

- 使用 `get_database_url(unittest=True)` 连接 `ragf_test` 库（独立于开发库）
- 提供 `override_get_db` / `override_get_db_transaction`，配合 FastAPI `app.dependency_overrides` 注入

## 6. 覆盖情况结论

| 用户框定内容 | 是否已做 | 说明 |
| --- | --- | --- |
| 连接引擎 `create_async_engine` | ✅ | 池参数、探活、多数据源、lifespan 释放 |
| 会话工厂 `async_sessionmaker` | ✅ | 命名数据源 + `begin()` 事务上下文 |
| ORM 模型（SQLAlchemy） | ✅ | 基类/Mixin/类型兼容/雪花主键，22 模型实测注册 |
| Alembic 迁移脚本 | ⚠️ 占位 | 配置与 env.py 就绪；**未上线策略，`versions/` 仅占位**，建表走 `create_all`（见 4.2） |
| `get_db()` 依赖注入 | ✅ | 含事务变体与 Annotated 类型别名 |
| 生命周期管理（lifespan） | ✅ | `LifespanManager` 三阶段编排，启动建表、关闭释放连接池（见 2.4） |
| 数据库初始化操作 | ✅ | lifespan 自动建表 + `task backend:init-db`（建表/Redis 检查） |
| 测试库隔离 | ✅ | `ragf_test` + override 依赖 |

## 7. 已知缺口

- **Alembic 迁移为占位（有意为之）**：未上线阶段不生成版本脚本，结构变更靠 `create_all` 覆盖；上线前必须补基线并统一迁移入口（见 4.2）
- **连接池监控未接入**：`db.py` 留有 TODO，后续可接 Prometheus SQLAlchemy instrumentation（依赖已引入）
- **`DATABASE_PK_MODE` 语义偏弱**：主键固定雪花生成，该开关仅影响序列化与代码生成，需在团队内明确约定
- 迁移与 `create_all` 并存时存在双写风险：引入 Alembic 后应统一入口，避免两套建表路径产生漂移
