# 消息队列基础设施设计（异步骨架）

## 1. 概览

消息队列是系统异步能力的基础设施，支撑定时任务、异步清理、后台执行等场景，核心位于 `backend/src/app/task/`：

| 内容 | 状态 | 位置 |
| --- | --- | --- |
| Celery 应用与配置 | ✅ 已实现 | `backend/src/app/task/celery.py` |
| Broker（Redis / RabbitMQ 双支持） | ✅ 已实现 | 同上，由 `CELERY_BROKER` 切换 |
| 结果后端（数据库） | ✅ 已实现（自定义 Backend） | `backend/src/app/task/database.py` |
| 任务定义与自动发现 | ✅ 已实现 | `tasks/`、`celery.py: find_task_packages` |
| 定时调度（Beat + DatabaseScheduler） | ✅ 已实现 | `backend/src/app/task/utils/schedulers.py` |
| 任务管理 API | ✅ 已实现 | `backend/src/app/task/api/` |
| 部署（supervisor：worker/beat/flower） | ✅ 已配置 | `deploy/backend/supervisor/` |

**技术选型**：

- 任务框架：Celery（`celery_aio_pool` 支持异步任务池）
- Broker：开发默认 **Redis**（db 1），生产 `prod` 环境自动切换 **RabbitMQ**
- 结果后端：**数据库**（PostgreSQL `psycopg` / MySQL `pymysql`），不依赖 Redis 存结果
- 调度：`DatabaseScheduler`，调度表存数据库，Redis 做分布式锁与变更通知
- 监控：Celery 事件开启 + Flower（supervisor 已配置）+ OpenTelemetry 埋点（`GRAFANA_METRICS_ENABLE` 时）

## 2. 架构

```text
FastAPI (Web 进程)
  │  send_task / .delay
  ▼
Celery Broker ── Redis db:1（开发） / RabbitMQ（生产）
  ▼
Celery Worker ── asyncio 池（本地）/ gevent 池（部署）
  │  执行任务（可写业务库 / 调服务层）
  ▼
结果后端 DatabaseBackend ── task_result / task_set_result 表（PostgreSQL / MySQL）
  │
  └── Beat 进程（DatabaseScheduler）── Redis 锁 fba:celery:beat_lock + task_scheduler 表
```

三个独立进程（与 Web 进程解耦，互不影响）：

| 进程 | 命令 | 说明 |
| --- | --- | --- |
| Web | `task dev` | FastAPI 应用，负责任务投递与管理 API |
| Worker | `task worker` | 消费任务；部署用 supervisor `-P gevent -c 1000` |
| Beat | `task beat` | 定时调度器；部署用 supervisor 托管 |

> Worker / Beat **不走 FastAPI lifespan**，使用独立连接（结果后端为同步引擎），与 Web 进程的 `async_engine` 互不影响（见 [数据库层设计](数据库层设计.md) 2.4）。

## 3. Broker 与结果后端

### 3.1 Broker

- `CELERY_BROKER = 'redis'`（默认）：`redis://:{password}@{host}:{port}/{CELERY_BROKER_REDIS_DATABASE}`，**与缓存/限流共用 Redis 实例，逻辑库隔离**（broker 为 db 1）
- `CELERY_BROKER = 'rabbitmq'`：`amqp://{user}:{pass}@{host}:{port}/{vhost}`；`ENVIRONMENT=prod` 时由 `config.py check_env` **自动切换**为 RabbitMQ
- `broker_connection_retry_on_startup=True`：启动时 broker 不可用自动重试

### 3.2 结果后端（数据库）

`celery.py` 组装 `db+postgresql+psycopg`（或 MySQL `db+mysql+pymysql`）连接串，并通过 `app.loader.override_backends` 指向自定义 `DatabaseBackend`（`backend/src/app/task/database.py`）：

- **重写原因**：Celery 内置数据库后端与项目模型/建表/迁移配合不佳（注释原文），重写后结果表并入项目 `MappedBase` 统一管理
- `SessionManager`（`backend/src/app/task/session.py`）：`prepared=True` 禁止自动建 celery 内部表，避免与项目建表冲突
- 结果表模型（`backend/src/app/task/model/result.py`）：
  - `task_result`：任务 ID / 状态 / 结果 / traceback / 完成时间，`result_extended=True` 时启用 `TaskExtended`（含 name/args/kwargs/worker/retries/queue）
  - `task_set_result`：任务集结果

## 4. 任务定义

### 4.1 自动发现

`find_task_packages()` 扫描 `tasks/` 下所有含 `tasks.py` 的目录并 `autodiscover_tasks`，新增任务目录无需手工注册。

### 4.2 任务基类

`backend/src/app/task/tasks/base.py` 的 `TaskBase`：

- `autoretry_for = (SQLAlchemyError,)`：数据库错误自动重试
- `max_retries = CELERY_TASK_MAX_RETRIES`（默认 5）
- 生命周期钩子：`before_start` / `on_success` / `on_failure` 通过 **Socket.IO 推送任务状态通知**（前端实时可见）

### 4.3 示例任务（`tasks/tasks.py`）

| 任务 | 类型 | 说明 |
| --- | --- | --- |
| `task_demo` | 同步 | 模拟 30s 耗时操作 |
| `task_demo_async` | 异步（async def） | 异步池执行示例 |
| `task_demo_params` | 异步 | 传参示例 |
| `delete_db_opera_log` / `delete_db_login_log` | 异步（shared_task） | 定时清理操作/登录日志 |

> 项目内业务代码通过 `celery_app.send_task(name=..., args=..., kwargs=...)` 或 `.delay()` 投递；可选队列/交换机/路由键在任务调度中配置。

## 5. 定时调度（Beat）

### 5.1 双层调度来源

| 来源 | 说明 |
| --- | --- |
| 本地静态调度 | `get_local_beat_schedule()`（`tasks/beat.py`）：示例任务 + 日志清理，启动时写入调度表 |
| 数据库调度 | `task_scheduler` 表，支持运行期增删改、启停、手动执行 |

### 5.2 DatabaseScheduler（`utils/schedulers.py`）

- `TaskScheduler` 表字段：任务名/任务、args/kwargs、queue/exchange/routing_key、start_time、expire、类型（`INTERVAL=0` / `CRONTAB=1`）、`one_off`、`enabled`、`total_run_count`、`last_run_time`
- **变更感知**：SQLAlchemy 事件（insert/update/delete）写入 Redis `fba:celery:last_update`，调度器 `schedule_changed()` 检测后同步内存调度，`max_interval=5s` 保证变更分钟级生效
- **分布式锁**：`beat_init` 时抢 `fba:celery:beat_lock`（Redis Lock），防止多 Beat 实例重复调度；`tick` 时续期、`close` 时释放
- 时区支持：`TzAwareCrontab`（`utils/tzcrontab.py`）解析 5 段 crontab 表达式，`crontab_verify` 校验
- 任务到期：`start_time` 之后才执行；`one_off` 执行一次后自动禁用；非法计划/参数自动禁用并记录日志

### 5.3 调度管理

通过任务管理 API（见第 6 节）创建 interval / crontab 两种调度，创建时校验 crontab 合法性，重复名称拒绝。

## 6. 任务管理 API

路由前缀：`/api/v1/tasks`、`/api/v1/task-results`、`/api/v1/schedulers`（`backend/src/app/task/api/router.py`）

| 端点 | 功能 | 权限 |
| --- | --- | --- |
| `GET /tasks/registered` | 已注册任务列表（inspect Worker） | `DependsJwtAuth` |
| `DELETE /tasks/{task_id}/cancel` | 撤销任务 | `sys:task:revoke` + RBAC |
| `GET /task-results` / `/{pk}` | 分页/详情查询任务结果 | `DependsJwtAuth` |
| `DELETE /task-results` | 批量删除任务结果 | `sys:task:del` + RBAC |
| `GET/POST /schedulers`、`PUT/DELETE /schedulers/{pk}` | 调度 CRUD 与启停 | `sys:task:add/edit/del` + RBAC |
| `POST /schedulers/{pk}/execute` | 手动立即执行调度任务 | `sys:task:exec` + RBAC |

- 撤销/执行前先 `control.ping()` 探测 Worker，不可用返回明确错误
- 前端实时状态：Socket.IO 事件 `task_worker_status`（`backend/src/app/task/actions.py`）

## 7. 配置项

| 配置 | 默认 | 说明 |
| --- | --- | --- |
| `CELERY_BROKER` | `redis` | broker 类型；`prod` 自动切 `rabbitmq` |
| `CELERY_BROKER_REDIS_DATABASE` | 必填 | Redis broker 逻辑库（建议 db 1） |
| `CELERY_RABBITMQ_HOST/PORT/USERNAME/PASSWORD` | 必填 | RabbitMQ 连接 |
| `CELERY_RABBITMQ_VHOST` | 空 | 虚拟主机 |
| `CELERY_REDIS_PREFIX` | `fba:celery` | 调度锁/变更通知键前缀 |
| `CELERY_TASK_MAX_RETRIES` | 5 | 数据库错误自动重试上限 |
| `GRAFANA_CELERY_OTEL_SERVICE_NAME` | `fba_celery_worker` | OTEL 服务名（Grafana 面板引用） |

字段覆盖见 [配置清单](配置清单.md)「消息队列」行；三层 env 分层见 [环境变量](环境变量.md)。

## 8. 启动与部署

本地开发（`backend/Taskfile.yml`，均已前置 `env-check`）：

```bash
task dev          # Web
task worker       # celery worker -A backend.src.app.task.celery:celery_app
task beat         # celery beat（DatabaseScheduler）
```

容器部署（`deploy/backend/supervisor/`）：

| 程序 | 命令要点 |
| --- | --- |
| `ragf_server` | `uvicorn backend.main:app --port 8001` |
| `ragf_celery_worker` | `celery ... worker -P gevent -c 1000` |
| `ragf_celery_beat` | `celery ... beat` |
| `ragf_celery_flower` | `celery ... flower --port=8555`（默认账号 `admin:123456`，部署应修改） |

## 10. 已知缺口

- **部署 worker 使用 gevent 池**（`-P gevent -c 1000`），本地 `task worker` 使用 asyncio 池，两套池并存需在业务任务中保持兼容（勿在任务内混用线程/异步 API 假设）
- **Beat 分布式锁依赖 Redis 单点**：Redis 故障时调度暂停；高可用部署需评估 Redis 集群或外部锁
- **结果存储使用 `PickleType`**：仅信任来源的任务可写，多语言消费者不可直接解析；跨版本 pickle 兼容需留意
- **无死信/重试队列规划**：当前仅 `SQLAlchemyError` 自动重试，业务级失败处理与死信策略待补充
- **Flower 默认凭证** `admin:123456` 仅限内网，生产需通过环境变量覆盖
