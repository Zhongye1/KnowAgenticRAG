## 1. 设计原则

1. **同步只读路径**：检索方法持有 db 会话但不写库、不派任务；摄取（写路径）归 ingest 域，问答（生成路径）归 chat 域。
2. **核心能力失败上抛，可选能力失败降级**：embedding / 召回失败直接抛异常（不做 `except → return []` 式伪装成功）；精排是可选能力，失败降级为召回序并打 `degraded` 标记 + 结构化日志 + 指标。
3. **PG 为事实源，Milvus 为检索镜像**：命中条目的正文、文件名、token 数一律回查 PG 补全；Milvus 侧字段仅供召回与过滤。
4. **过滤在召回内部发生、由服务端构造**：权限与文档过滤都下推为 Milvus 标量表达式，在召回时生效（不是召回后过滤）；客户端只能传"意图"（如 `filters`），不能传过滤表达式本身。
5. **指标只打在域门面与外部依赖边界**：span / metrics 挂在 `RetrievalService` / `ChatService` 门面，不侵入纯函数（`filters.py` / `params.py` / `prompts.py` 均无 IO、可直测）。

## 2. 总体链路：五步编排

入口有三类，全部收敛到同一个编排门面 `RetrievalService._aggregate`（`retrieval/service/retrieval_service.py`）：

- REST：`POST /api/v1/knowledge_bases/{kb_name}/search`（`retrieval/api/v1/search.py`，JWT + RBAC + `rag:kb:search` 权限点）
- 问答：`ChatService._prepare` 先检索再生成（见 §9）
- MCP：`search_knowledge` / `answer_with_citations` 工具（PAT 鉴权，复用同一门面）

```text
query_text + param（覆盖层）+ scope（ACL 范围）
  │
  ▼
① 装配校验      多 KB 去重（≤20 库，M11）→ 逐库归属校验（跨租户不可见 = NotFound）
  │             scope.allowed_kbs 求交：请求库 ∉ 授权集 → Forbidden（防工具版 IDOR，D33）
  ▼
② embedding     按 KB 的 embedding 模型分组（同模型共享一次编码调用）
  │             模型 spec 取 KB 登记值，缺省兜底 dashscope:qwen3.7-text-embedding-flash
  │             （与摄取侧同源，防止两侧向量空间错配）；返回空 → 上抛
  ▼
②b 视觉编码     include_visual 开启时：查询文本经视觉编码器编码（qwen3-vl-embedding，
  │             与摄取侧同一向量空间，指纹守卫）；失败按可选能力降级，不阻塞文本
  ▼
③ 过滤 + 召回   逐 KB：文档级过滤（file_name / filters）经 PG 解析为 document_id 集
  │             → 组合 Milvus 表达式（doc_ids AND version_id AND scope ACL）
  │             → 策略注册表 RETRIEVE_STRATEGIES[mode]（vector / hybrid，默认 hybrid）
  │             → search_ragf_kb：Milvus 服务端召回（hybrid = dense+BM25 双路 RRF）
  │             可选视觉召回：同一 doc/ACL 表达式（无版本标量）→ search_visual
  ▼
④ 精排（可选）  use_reranker 时：候选截断 ≤300 → CrossEncoder 重打分 → 按 rerank_score 降序
  │             失败/超限 → 降级为召回序（reranked=False, degraded=True + 指标）
  │             视觉命中不进精排（EagleRAG 语义：tile 与文本分数不可比）
  ▼
⑤ 补全组装      回查 PG chunks + documents（正文/文件名/token_count）
                → active_version 收敛（显式 version_id 请求时不收敛）
                → 截取 final_top_k → KBSearchOutput（results + 独立 visual_results）
```

多 KB（`search_multi`）：各库独立走 ③（结果带 `kb_name` 归属）→ 合并后统一走 ④⑤，精排与 `final_top_k` 全局生效。单 KB（`search`）是 `kb_names=[one]` 的特例。

### 2.1 REST 查询面（/rag，对齐 EagleRAG）

| 端点 | 说明 |
| --- | --- |
| `POST /api/v1/rag/search` | **canonical 检索端点**：`kb_names`（1-20 跨库，旧路径式端点已移除）+ `document_ids` 直推（跳过 PG 解析，≤500）；响应 `sources{text[], image[]}` 二元来源 + `route`（selector=explicit，无 LLM 路由）+ `steps`（recall/rerank/hydrate 轨迹），字段对齐 EagleRAG SearchResponse |
| `POST /api/v1/rag/search/stream` | 检索 SSE：事件 `step*` → `sources` → `done`（summary 含 route/steps/计数）；语义错误统一 `error{code, message}`（PERMISSION_DENIED/KB_NOT_FOUND/INVALID_REQUEST/INTERNAL） |
| `GET /api/v1/rag/images/{image_id}/url` | 视觉 tile 预签名回源：Milvus 定位 → PG 文档存在性校验 → 预签名 URL（与文档下载同鉴权模式，`rag:kb:read`） |

实现上五步编排事件化为 `RetrievalService._asteps`（步骤完成即时产出），`search/search_multi` 经 `_collect` 消费（同步语义不变），SSE 走 `astream_search`（span/指标同规）。`sources.image` 的 `image_path` 为 MinIO 对象键，前端经 images 端点换短期直链。

## 3. 检索参数：三层合并

参数优先级 **request > KB `query_params` > settings**（D17），白名单键 + 轻量强转，非法值跳过该层覆盖（`retrieval/service/params.py: merge_search_params`）。出厂商默认（`core/config.py`）：

| 参数                  | 默认值                              | 说明                                                       |
| --------------------- | ----------------------------------- | ---------------------------------------------------------- |
| `search_mode`         | `hybrid`                            | `vector` / `hybrid`                                        |
| `recall_top_k`        | 20                                  | 召回候选数（精排输入）                                     |
| `final_top_k`         | 5                                   | 最终返回条数                                               |
| `similarity_threshold`| 0.2                                 | **仅 vector 模式**的余弦阈值；hybrid 为 RRF 秩分，不适用   |
| `use_reranker`        | `true`                              | 是否精排（D16）                                            |
| RRF k                 | 60（`RAGF_RETRIEVAL_RRF_K`）        | 服务端 RRFRanker 参数                                      |
| nprobe / nlist        | 10 / 1024                           | dense IVF_FLAT 搜索/建索引参数                             |
| rerank 模型           | `dashscope:qwen3.7-text-rerank`     | `RAGF_RETRIEVAL_RERANK_SPEC`                               |
| `include_visual`      | `false`（`RAGF_RETRIEVAL_USE_VISUAL`） | 是否附带视觉召回（ragf_visual 集合，见 §4.1）            |
| `visual_top_k`        | 5（`RAGF_RETRIEVAL_VISUAL_TOP_K`）  | 视觉召回条数上限（视觉不进精排）                           |

召回数解析（`resolve_recall_top_k`）：开精排时 `recall = max(recall, final)`（精排需要候选池），否则 `recall = final`（不精排时多召回无意义）。

## 4. 召回策略（vector / hybrid）

策略以注册表分发（`retrieval/service/strategies/__init__.py: RETRIEVE_STRATEGIES`），上下文 `ctx` 携带 kb_name / query_text / query_embedding / dim / recall_top_k / 阈值 / 过滤表达式 / namespace。两者最终都落到 `database/milvus_kb_ops.py: search_ragf_kb` 的同步调用（经 `asyncio.to_thread` 包装，遵守异步纪律）：

| 模式     | 召回方式                                                                                                                          | 分数语义       | 阈值过滤 |
| -------- | --------------------------------------------------------------------------------------------------------------------------------- | -------------- | -------- |
| `vector` | 单路 dense：`embedding` 字段 COSINE + nprobe，取 top-`recall_top_k`                                                                | 余弦相似度     | 应用     |
| `hybrid` | 双路：dense（COSINE）+ sparse（`content_sparse` BM25），两路 limit 均为 `recall_top_k`（防 RRF 尾段截断）→ **服务端** `RRFRanker(k)` 融合 | RRF 秩分 Σ1/(k+rank) | 不适用   |

hybrid 模式下候选纯度交由精排段保证（§8）——这是"RRF 分数不是相似度"的直接推论，也是默认 `use_reranker=true` 的原因。

### 4.1 视觉召回（ragf_visual，可选）

在文本召回之外，`include_visual` 开启时对 `ragf_visual` 集合做一轮独立视觉召回（双管线摄取 spec D7 的查询侧；EagleRAG `pixelrag_visual_retriever` 语义）：

- **编码**：查询文本经视觉编码器（`model_provider/providers/visual.py`，DashScope qwen3-vl-embedding）编码——图片与文本共享同一向量空间；该编码器同时服务摄取写入侧，provider:model:dim 变更会触发集合指纹守卫。整次查询只编码一次，同步编码器经线程池调用。
- **过滤**：与文本集合同构——document_id 集（文档级过滤解析结果）+ scope ACL 表达式直接下推（视觉集合带同名 ACL 标量字段）；**视觉行无 version 标量，不做版本过滤**。
- **结果形态**：视觉命中以 `visual_results` **独立返回**（tile 元数据：image_path / page / position / chunk_type / score），不混入 `results` 文本候选——视觉文档没有 PG chunks（`content_summary`/`source_chunk_id` 预留为空），无法进入"回查 PG → 精排 → 引用"的 chunk 链路，也不参与 D24 引用编号。多 KB 场景逐库召回后按视觉相似度全局降序截断 `visual_top_k`。
- **降级**：编码或召回失败 → `visual_degraded=true` + `ragf.retrieval.visual_degraded` 指标 + warning 日志，文本结果不受影响（可选能力语义，同精排）。
- **消费**：REST `search` 直接返回；chat 请求可用 `include_visual` 开启，命中数经 SSE `meta.visual_count` 透出（图片呈现与前端契约另行设计）；MCP 工具面暂不透出该参数。

## 5. 向量库：模板集合、索引与多租户

### 5.1 共享模板集合

全部 KB 共享 `ragf_text_{dim}` 模板集合（默认 `ragf_text_1024`），库间靠 `kb_name` 标量过滤隔离；`kb_name` 过滤表达式由 `milvus_kb_ops` 层**统一注入**，调用方无法绕过。集合 schema（`milvus_kb_ops.py: _ragf_text_schema`）：

| 字段            | 类型                | 说明                                                         |
| --------------- | ------------------- | ------------------------------------------------------------ |
| `chunk_id`      | VARCHAR 主键        | `{document_id}:{version_id}:{idx}`                           |
| `embedding`     | FLOAT_VECTOR(dim)   | dense 向量（千问 text-embedding，1024 维）                   |
| `content`       | VARCHAR(65535)      | 分块原文，开 Milvus 内建中文 analyzer（jieba）               |
| `content_sparse`| SPARSE_FLOAT_VECTOR | **不手工计算**：由集合级 BM25 Function 在服务端从 `content` 生成 |
| `kb_name` / `document_id` / `version_id` / `chunk_index` | 标量 | 库隔离 / 文档过滤 / 版本过滤 / 块序                        |
| `namespace`     | VARCHAR，**分区键** | 租户域，检索时租户硬边界（§6）                               |
| `visibility` / `owner_id` / `groups` | 标量 | 文档级 ACL 镜像（DB 为事实源），变更经 `update_ragf_document_acl` 传播 |

索引：dense `IVF_FLAT`（COSINE，nlist=1024）、sparse `SPARSE_INVERTED_INDEX`（DAAT_MAXSCORE）、`kb_name`/`document_id`/`visibility`/`owner_id`/`groups` 各建倒排；`namespace` 为分区键由 Milvus 自管理。

### 5.2 升级护栏

集合 schema 指纹（字段名/类型 + BM25 Function + dim + ACL 字段）与代码不匹配时：**可证明为空才自动重建；非空或无法判定一律 `RuntimeError` 拒绝启动**，防止静默丢数据（`ensure_ragf_template_collection`）。

### 5.3 租户隔离的两层实现

- **连接层**：`database/milvus_pool.py` 按 `plugin_namespace → Milvus Database` 映射缓存客户端（`core → default`，其余同名字库），不同实例域物理分库；
- **数据层**：集合内 `namespace == ?` 过滤表达式 + 分区键剪枝，兜住同库多租户。

## 6. 检索范围（ACL 下推）

Scope 构建与表达式生成收口在 `retrieval/service/scope.py`，三层递进：

| 层次   | 机制                                                                                                                              |
| ------ | --------------------------------------------------------------------------------------------------------------------------------- |
| 租户   | namespace 与请求头一致（只能"选"不能"越"）；Milvus 侧 `namespace ==` 表达式 + 分区键 + 连接分库                                   |
| KB 级  | `rag_kb_acl` 表按用户组（本人 ID + 部门链）求 `allowed_kbs`；**表为空时向后兼容返回全部 KB**；请求库与授权集求交，越权 403         |
| 文档级 | `visibility == "public" or owner_id == user or array_contains_any(groups, [...])`，直接编译进 Milvus 召回表达式                   |

用户组展开：本人 ID + 直属部门 + 沿 `sys_dept.parent_id` 的祖先链（防循环、限深 20），部门树变更天然跟随。安全细节：

- 进入表达式的 ID 全部过 `[A-Za-z0-9_-]+` 白名单（防注入），单表达式 ID 数上限 200；
- 无任何 KB 权限时返回 `namespace == "__no_access__"` 恒假表达式（不报错、返回空）；
- scope 由 `build_retrieval_scope()` 在服务端构建（HTTP 路由与 MCP 各自提供 `UserContext`），客户端不可传入任何过滤语义。

## 7. 结构化过滤与版本收敛

`KBSearchParam.filters`（`RetrievalFilters`，D26/M11）支持 `keyword / tag / version_id / updated_after / updated_before / file_type / path_prefix`，与 legacy `file_name` 关键词过滤在服务层合并。处理分两段：

1. **文档级 → 表达式**（`filters.py: compose_retrieval_expr`）：`keyword/tag/updated/file_type/path_prefix` 经 kb 域文档登记（PG）解析为 `document_id` 集，再编译为 `document_id in [...]`；解析命中超过 `MAX_DOC_FILTER_MATCH`（500）个文档时直接报错要求缩小范围，防一次性拉全库。
2. **版本过滤与收敛**：显式 `version_id` 直接编译为 `version_id == n` 进表达式（此时不做收敛，支持跨版本对比）；否则召回后按 PG `documents.active_version` 收敛（`filter_active_versions`），来源补全缺行的命中保留——不因补全缺失误伤召回。

## 8. 精排：可选能力，失败降级

- 模型：`RAGF_RETRIEVAL_RERANK_SPEC`（默认 `dashscope:qwen3.7-text-rerank`），经 model_provider 模型工厂获取，用完即 `aclose()`。
- 候选截断：`MAX_RERANK_CANDIDATES = 300`，防御多 KB × 大 recall 的越界成本。
- 打分：`acompute_score(query, docs, normalize=True)` → `rerank_score` → 降序排序。
- **降级面**：任何异常（模型未配置 / 上游失败 / 分数长度不符）→ 返回召回序、`degraded=True`、`ragf.retrieval.rerank_degraded` 计数 + warning 日志。调用方通过输出 payload 的 `reranked` / `degraded` 字段感知，不需要捕获异常。

## 9. 问答生成（chat 域）

`ChatService` 门面 = `prepare`（检索 → 引用/上下文组装 → 模型解析）+ 事件产出，`retrieval_service` 是唯一检索来源（域依赖方向 `mcp → chat → retrieval`，D18）。

两条 REST 形态共用同一 `prepare` 产物（EagleRAG `query`/`query_stream` 同构，仅生成调用分阻塞/流式）：`POST .../chat` 同步返回 `ChatResponse`，`POST .../chat/stream` 走 SSE。流式检索编排经 `_prepare_stream` 消费 `retrieval_service.astream_search`，`step` 事件即时透传；同步 `_prepare` 消费同一 `_asteps` 编排的收敛结果（`_collect`），故两条路径产物一致。

### 9.1 输入投影与上下文组装

`ChatParam` 中与检索重合的键（`query_text/search_mode/recall_top_k/.../file_name/filters`）经 `to_search_param` 投影为检索覆盖层——**问答请求天然继承 §3 的三层参数体系**。上下文组装（`chat/service/prompts.py`，纯函数）：

- 引用编号：命中条目按 D24 连续编号 `[1..n]`（`build_citations`）；
- 预算裁剪：按 `RAGF_CONTEXT_MAX_TOKENS`（4096）从高到低整块保留，token 粗估 = ASCII/4 + CJK×1，块开销另计 40；
- 消息结构：`system（行为约束 + 【片段n】来源/版本 + 原文）+ 近 10 轮 history + user（问题 + 随问附件块）`；服务端无会话状态，history 由调用方显式传入、只做近 N 轮截断；
- 系统提示词核心约束：只依据片段作答、不足时明说、引用用 `[n]` 标注（可溯源）。

### 9.2 SSE 事件契约（D25）

`astream` 经 `EventSourceResponse` 输出事件序列（`step*` → `meta` → `citation` → `delta*` → `usage` → `done`），语义错误也统一走 `error` 事件（调用方无需同时解析 JSON 错误与流错误两条路径）：

| 事件       | 时机与负载                                                                          |
| ---------- | ------------------------------------------------------------------------------------ |
| `step`     | 检索编排即时产出 `{name: recall/rerank/hydrate, detail}`                             |
| `meta`     | kb_name / mode / model_spec / hit_count / visual_count                               |
| `citation` | 引用条目全集（已按预算裁剪，`n` 与回答中 `[n]` 对应）+ `images[]`（视觉命中卡片，`include_visual` 开启时；不占 `[n]` 编号） |
| `delta`    | 模型流式增量 `{content}`                                                             |
| `usage`    | token 用量（缺省补 0）                                                               |
| `done`     | 自包含：`reason=complete | max_tokens | empty_result` + `answer` + `kb_name/kb_names/mode/model_spec/hit_count/visual_count` + `route` + `steps` + `usage` |
| `error`    | `{code, msg, trace_id}`，code ∈ `KB_NOT_FOUND / INVALID_REQUEST / MODEL_NOT_CONFIGURED / STREAM_ERROR / INTERNAL` |

关键分支：**无命中短路**（`hit_count=0` → 发 `empty_result` 文案，不调用模型，省一次无意义生成）；**模型解析失败不进异常面**（`model_error` 随 `PreparedChat` 带回，统一转 `error` 事件）。chat 模型 spec 来自请求 `model` 或 `RAGF_CHAT_MODEL_SPEC`（空 = 必须显式指定）。

### 9.3 非流式

`acomplete`（单 KB，`POST .../chat`）/ `acomplete_multi`（多 KB，MCP `answer_with_citations` 批次面）与流式共用 `prepare` 语义，返回字段为各流式事件负载的并集：`{answer, reason, citations[], images[], route, steps[], usage, hit_count, visual_count, mode, model_spec}`；无命中同样短路为 `reason=empty_result` + 约定文案。

## 10. 多 KB 聚合（M11/D27）

- 上限 `MAX_KB_NAMES = 20`，去空去重后逐库校验归属；
- **按 embedding 模型分组编码**：同模型的库共享一次向量调用，跨模型库各自编码；
- 逐库独立召回（各自的表达式与阈值）→ 合并 → **统一精排与 final_top_k**（跨库分数可比性由精排保证，RRF 秩分跨库不严格可比）；
- 每条命中带 `kb_name` 归属，引用与来源信息可区分库。

## 12. 现状边界与演进
