# 任务队列规划（Spec）

> 上游文档：[2026-08-25-rag-api设计与落地路线.md](../2026-08-25-rag-api设计与落地路线.md) §阶段 0
> 状态：方案已选定，待实现

## 1. 现状

`init_celery()`（backend/src/app/task/celery.py）当前未定义 `task_queues` / `task_routes`——所有任务进默认的 `celery` 队列。现有任务均为轻量级（`task_demo` 系列、`db_log` 操作日志落库），单队列无冲突。其他现状：

- **Broker 双轨制**：dev 用 Redis，prod 由 validator 强制切 RabbitMQ；队列声明写在 Celery 层则两种 broker 通吃（Celery Queue('parse') 在 Redis 下是同名 list key，在 RMQ 下是真正的 AMQP queue）
- **自动发现**：`find_task_packages()` 扫描 `tasks/` 下含 `tasks.py` 的包
- **Worker 启动**：Taskfile 的 `worker` 任务不带 `-Q`，只消费默认队列

## 2. 需求

| # | 需求 | 单队列为何不满足 |
|---|---|---|
| 1 | 资源隔离 | parse 是分钟级 CPU 密集任务，会堵住 db_log 等秒级任务 |
| 2 | 独立扩容 | 解析积压时只想多开 parse worker，单队列无法按类型伸缩 |
| 3 | 管道串联 | parse→embed→index 三步依赖传递，需要链式触发与失败重试边界 |
| 4 | 可观测 | `/ingest/queue-metrics` 要按队列报深度/并发数，分队列才有分队列指标 |
| 5 | 不破坏现状 | demo/db_log/beat 任务继续走默认队列，RAG 任务只增不改 |

本质：**保持 task app 单一入口不动，为 RAG 管道预留三条车道 + 一条兜底道，且路由对新增任务零维护成本。**

队列资源特征：

| 队列 | 任务 | 特征 |
|---|---|---|
| `parse` | PDF/URL 解析、Knowhere 调用 | CPU/外部 IO 密集、慢（秒~分钟级） |
| `embed` | 批量 embedding | API 限流敏感、吞吐受 LLM 服务制约 |
| `index` | 写 Milvus、更新审计状态 | 快、轻量 |
| `celery` | 默认兜底：demo/db_log/beat 等 | 保持现状 |

## 3. 方案

**摄取走异步队列（Celery + Rmq），查询走同步在线路径（不经任何队列）**。队列只承载长耗时的离线工作，在线请求保证低延迟。

## 一、摄取侧：4 条队列的接力流水线

### 队列定义与路由

定义队列，定义路由表和并发：

| 队列 | 并发 | 承载任务 | 设计理由 |
| --- | --- | --- | --- |
| `router_queue` | 4 | `ingest_router` | 分诊轻量，高并发保入口不积压 |
| `knowhere_queue` | 8 | `knowhere_parse`、`knowhere_visual_chunks` | IO 密集（SDK/HTTP 解析），可放大并发 |
| `pixelrag_queue` | 1 | `pixelrag_build`、`knowhere_visual_chunks` | GPU/大内存渲染，**刻意串行防 OOM** |
| `dead_letter` | — | 重试耗尽的任务 | 兜底 + 管理端重放 |

### 接力方式： Celery canvas

```
① API POST /ingest
   └─ runner.ingest() [ingest/runner.py:118]  ← 同步 FastAPI 进程内
      去重(sha256+kb_name) → 上传 MinIO → 注册审计(PENDING)
      └─ app.send_task("ingest_router", queue="router_queue")

② ingest_router [ingest/router.py:331, @with_retry]
   probe_pdf_form 表单探针 + 路由决策
   ├─ 文本型 ─► send_task("knowhere_parse", queue="knowhere_queue")
   └─ 视觉型 ─► send_task("pixelrag_build", queue="pixelrag_queue")

③ knowhere_parse [knowhere_adapter.py:770]
   SDK 解析 → upsert_text_nodes(Milvus) → 关键词目录(PG) → doc_nav
   ├─ 有图表/图片块 ─► dispatch_visual_chunks
   │                    └─ send_task(queue="pixelrag_queue")  [knowhere_adapter.py:680]
   └─ 无视觉块    ─► 状态推进 SUCCESS

④ pixelrag_build [pixelrag_adapter.py:329]
   渲染 tile → Qwen3-VL 编码 2048d → upsert_visual(eagle_visual) → SUCCESS
```

每段独立重试/独立扩缩容；Milvus 写入是幂等 upsert，段失败重跑不会产生脏数据。

### 状态机与审计

定义严格的状态转移图，每个 job 在 PG 中留痕：

```
PENDING → RENDERING → EMBEDDING → INDEXING → SUCCESS
                ↘ RETRYING ↗     ↘ FAILED → (manual replay → PENDING)
```

- `transition()` 校验非法跳转（`InvalidStateTransitionError`）
- `_DOWNSTREAM_ACTIVE_STATES`：进入 EMBEDDING 后生命周期归下游任务所有，router 不再改写
- 每步 `append_log` 写结构化日志，API 可通过 `get_job_status` / 审计列表轮询
- 失败时触发通知（`_maybe_notify` → notifications）

### 可靠性三件套

1. **`@with_retry`**（tasks/dead_letter.py:66）：基于 Celery `autoretry_for` 的指数退避，`countdown = 60s × 2^n`，最多 3 次；基类 `DeadLetterTask.on_failure` 在最终失败时自动投递死信队列，管理端 `replay_dead_letter` 手动重放（FAILED→PENDING）
2. **消息可靠性**（celery_app.py:58-60）：`acks_late=True`（做完才 ack）+ `prefetch=1`（防长任务饿死后面的短任务）+ `reject_on_worker_lost`（进程崩溃消息回队）
3. **超时护栏**：硬限 3600s / 软限 3300s，软限预留 5 分钟让任务收尾并落 FAILED 状态

### 队列观测

celery beat 每 30s 跑 `sample_queue_metrics`（admin/metrics.py:25），对三条队列做 Redis `LLEN` 采样写入 `metric_sample` 表，管理端可看积压曲线。

### 插件扩展点

域插件通过 `PluginManager.collect_celery_modules()` 注册自己的 Celery 任务模块（celery_app.py:89），worker 启动时统一 import——插件任务可以挂到已有三条队列或自建队列。

### 入口去重的并发隐患与防线

`runner.ingest()` 的 `sha256+kb_name` 去重是 **check-then-act** 模式，检查与写入之间存在竞态窗口：

```
① POST /ingest(文件A) ─> 查重: 不存在 ─┐
② POST /ingest(文件A) ─> 查重: 不存在 ─┤ 两个请求均通过检查
③ ① 写入审计行                        │
④ ② 写入审计行   ← 重复入库（双份向量/冗余对象）
```

多 worker / 多副本部署下进程内锁无效。触发条件苛刻（同文件毫秒级并发到达），但批量脚本导库恰是最需要去重的场景。

三层防线（成本递增，1 为必做）：

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 1 | **PG 唯一约束兜底**（必做） | 审计表 `UNIQUE(sha256, kb_name)`；并发插入第二个事务 IntegrityError → 返回"已存在"并复用已有 job_id。唯一约束才是正确性保证 |
| 2 | Redis SETNX 抢锁（可选优化） | `SET dedup:{sha256}:{kb} job_id NX EX 300`；抢到才走流程，否则直接返回已有 job_id，避免白跑上传 |
| 3 | 前端防抖/按钮禁用 | 只解决人为双击，不构成防线 |

原则：**应用层去重只是快路径，数据库唯一约束才是最终真相。**

## 二、查询侧：零队列，纯在线编排

查询**完全不走 Celery**。`EagleRouterQueryEngine`（router/router_engine.py:108）在 API 请求上下文内同步完成：

```
POST /query 或 /query/stream (SSE)
  └─ route_query 路由分类（DeepSeek，决定 text/visual/hybrid）
  └─ 多路召回：KnowhereGraphRetriever / HybridTextRetriever / PixelRAGVisualRetriever
  └─ RRF 融合 + qwen3-rerank（router/rerank_fusion.py）
  └─ MultimodalEngine 组装上下文生成答案，流式经 SSE 推 token
```

唯一沾边的“异步”是附件图片的**懒解析**（attachments/parser.py）：上传时不进队列、不写 Milvus，只在查询时临时编码——把成本推迟到实际用到的那一刻。

## 三、设计取舍小结

| 决策 | 收益 |
| --- | --- |
| 三队列按资源特性分并发（IO 密集 8 vs GPU 串行 1） | 吞吐与稳定性解耦，GPU 段永不并行 |
| send_task 显式接力而非 chain | 各段可独立重试/重放/扩容，状态机清晰 |
| 死信队列 + 状态机持久化 PG | 失败可见、可重放，不丢任务 |
| 查询不入队 | P99 延迟不受摄取高峰影响 |
| acks_late + prefetch=1 | at-least-once 投递 + 队列公平调度 |

## 四、本项目落地适配

上述设计为参考架构，落到本项目时的裁剪与对齐：

### 队列命名与粒度

| 参考实现 | 本项目 | 说明 |
| --- | --- | --- |
| `router_queue`（独立） | 并入 `parse` 队列起步 | 分诊毫秒级，内部系统入口 QPS 低，单独成队是过度设计；规模上来再拆 |
| `knowhere_queue` | `parse` | 按动作而非组件命名——底层解析器换实现不用改队列 |
| `pixelrag_queue` | `embed`（并发刻意压低/串行） | 同上；视觉编码归入 embed 语义 |
| `index` | `index` | 写 Milvus + 状态推进 |
| `dead_letter` | `dead_letter` | 照单全收 |

最终四条：`parse` / `embed` / `index` / `dead_letter` + 默认 `celery`。

### 全盘采纳项

- 死信队列 + `DeadLetterTask.on_failure` 自动投递 + 手动重放
- `acks_late / prefetch=1 / reject_on_worker_lost` 三件套
- 软硬超时护栏（3600s/3300s）
- 严格状态机：`transition()` 校验非法跳转、下游状态认领、结构化 append_log
- Milvus 幂等 upsert 兜底重跑（at-least-once 必须配幂等消费，写入阶段 2 验收标准）
- beat 每 30s 采样队列深度落表（与 `/ingest/queue-metrics` 实时 inspect 并存）

### 补充约束

- **查询侧背压**：查询不入队保 P99 正确，但 LLM/rerank 过载时需有限流（复用 pyrate-limiter）与客户端超时熔断兜底，否则在线路径被拖垮而非排队
- **去重**：按上文三层防线实施，唯一约束必做
