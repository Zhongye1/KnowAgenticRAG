## 1. 背景与目标

### 1.1 背景

当前 Agent 是**请求内直跑的无状态单次运行**：外层 StateGraph 5 节点 + 内层 `create_agent` ReAct，4 个只读工具，`agent_runs` 只是请求结束后的 best-effort 终态审计。这套形态对「单轮检索问答」是合适的，且查询理解部分**领先 Yuxi**（`plan/grade/rewrite` 是 Yuxi 完全没有的）。

但要支撑本项目的目标形态（agentic RAG + 全形态技能 + 双向 MCP），有三处硬缺口：

1. **没有长任务容器**：技能要执行脚本、生成产物、跑子智能体调研，这些都不可能挂在 HTTP 请求里（现有 180s 墙钟一过即丢）；
2. **没有可挂起/可恢复的运行态**：文档要等索引（OSS → RAG 索引链路 → 回调）、写工具要等人审批——两者都需要把 Run 挂起、让出进程、事后恢复；
3. **没有工作区**：技能的文件系统投影、脚本执行、产物交付全部落在「一个受控目录」上，本项目目前只有 MinIO 里的知识库对象。

### 1.2 目标

1. 建立**工作区与沙盒**（Agent 能读写文件、执行受限命令、交付产物），作为全形态技能的前置；
2. 把 Agent 运行从 HTTP 请求里**搬进 Celery worker**，建立持久化 Run 状态机 + FIFO 队列 + 租约，支持长任务与多副本；
3. 建立**可挂起/可恢复**能力（Postgres checkpointer + interrupt/resume），承载两个挂起源：文档索引等待、工具审批；
4. 建立**中间件体系**，使 Skills 门控、动态工具、MCP 工具注入、摘要压缩、用量统计有统一挂载点；
5. 落地**智能体文档流**：上传 → OSS → 触发既有 RAG 索引链路 → 完成后回调状态 → 恢复 Run。

### 1.3 非目标

- **不引入 ARQ**（D66）：仓库已有 RabbitMQ + Celery 三队列，不引第二套队列；
- **不引入 DeepAgents**：延续 D39 结论；本清单只按需自研中间件，不为了 `skills`/`summarization` 中间件付 anthropic + google-genai 两个 SDK 的镜像代价；
- **不搬 Yuxi 的 `sandbox-provisioner` 独立服务**（D68）：一期用受限子进程，二期容器化；
- **不做 Agent 实体化**（D72）：`agents` 表、可配置可共享的智能体留到二期；
- **不做多租户级 Run 隔离调度**：FIFO 按「用户 + 线程」串行，与 Yuxi 对齐，不做全局优先级队列。

## 4. 关键决策

| #       | 决策                                                                                                                                                                                                                                 | 备选项与否决理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **D64** | **推翻 D40**：引入 LangGraph Postgres checkpointer（`langgraph-checkpoint-postgres` 的 `AsyncPostgresSaver`），独立连接池                                                                                                            | 备选：维持无 checkpointer。否决理由：D70 的两个挂起源（等文档索引、等审批）**必须**有可恢复的状态快照，否则「挂起」等于「丢任务」；《agentic-rag-落地改造清单》中 D40 的否决理由（避免额外表与连接池）在「引入长任务」后收益反转。备选：自己序列化图状态。否决理由：重造 LangGraph 的 channel/版本语义，成本远高于引一个官方包                                                                                                                                                       |
| **D65** | 引入 **LangChain `AgentMiddleware` 中间件体系**，图构建时按上下文装配中间件栈                                                                                                                                                        | 备选：继续用节点级策略 + 手工 hook。否决理由：Skills 工具门控必须**每次模型调用前**重算可见工具集（见技能清单 D74），动态 MCP 工具要在同一位置注入，审批要在工具调用处中断——这三个需求天然是 `awrap_model_call` / `awrap_tool_call` 钩子；散在 5 个节点里会失控。**不引 DeepAgents**（延续 D39），中间件按需自研                                                                                                                                                                     |
| **D66** | Run 运行时**复用现有 Celery + RabbitMQ**：新增独立 `agent` 队列（`RAGF_CELERY_AGENT_QUEUE`）+ `ragf_celery_agent_worker`，与既有 `ingest` / `knowhere` / `visual` 三队列并列；**租约与状态事实源仍在 PostgreSQL**（Celery 只做投递） | 备选：引入 ARQ（对齐 Yuxi）。否决理由：仓库已有 RabbitMQ + Celery + `celery-aio-pool` + beat + flower + exporter 全套运维面（`docker-compose.yml:257-430`），引 ARQ 等于并置两套异步栈，纯粹的运维负债。**关键认识**：Yuxi 用 ARQ + PG lease 的分工（投递 vs 事实）才是要点，队列实现可替换；Celery 自身的 `visibility_timeout` 对长任务不可靠，因此 lease/heartbeat 必须自建，这点与 Yuxi 一致                                                                                      |
| **D67** | 工作区采用**两级模型**：`UserWorkspace`（uid 根）+ `Project`（DB 行 → 宿主目录 `projects/<uuid>`）；一期只实现 **Project 级**，不暴露 UserWorkspace 根                                                                               | 备选：单层 per-conversation 临时目录。否决理由：技能投影与产物需要跨会话持久（同一用户下次进来还要能访问自己的技能与历史产物）；备选：直接暴露 uid 根。否决理由：把宿主用户目录暴露给沙盒，越权面过大（Yuxi 也是靠 `Project` 收敛，`workspace/paths.py:103,218`）                                                                                                                                                                                                                    |
| **D68** | 沙盒一期 = **受限子进程 + 临时目录**（`bubblewrap`/`nsjail` 可用则用，不可用降级为 `subprocess` + rlimit + 命令白名单 + 环境变量剥离）；二期容器化                                                                                   | 备选：直接容器化。否决理由：容器编排（provisioner 服务、镜像预热、卷映射、回收）是一个独立子系统，会阻塞技能落地。备选：搬 Yuxi 的 `sandbox-provisioner`。否决理由：它是独立服务 + `provisioner_client.py` 客户端协议，本项目没有对应基础设施，且它的能力面（远程沙盒供应商）超出当前需求。**红线**：沙盒内的命令在无 bubblewrap 时必须**默认拒绝执行**（fail-closed），不做「尽力而为」的隔离                                                                                       |
| **D69** | **智能体文档流 = OSS 优先 + 复用 RAG 索引链路 + 完成回调**：附件上传 MinIO → 落**每用户隐式知识库**的 `documents` 行 → 入队既有 `ingest.process_document` → 摄取完成在**事务提交后**发 Redis 事件 → 回调恢复等待中的 Run             | 备选：附件直接进 Project Workdir（对齐 Yuxi）。否决理由：Yuxi 的附件是「即时可用」的普通文件，**不索引**；本项目要的是 agentic RAG，附件必须进向量库才能被检索工具命中，所以必须走索引链路。备选：建独立 `agent_attachments` 表 + 独立摄取路径。否决理由：复制一条摄取链路，违背「复用」要求，且要重做限额/去重/审计/对账。备选：共享一个部署级 KB + 文档级 ACL 收窄。否决理由：依赖「KB 公开 + 文档收窄」的绕法表达个人文档，语义别扭；每用户隐式 KB 的 `owner_id` 直接就是隔离边界 |
| **D70** | Run 状态机 = Yuxi 的 7 态**直接沿用**，**新增 1 态 `waiting_ingest`**。最终 8 态：`queued / running / waiting_ingest / interrupted / cancel_requested / cancelled / completed / failed`                                              | 备选：另起一套状态命名。否决理由：Yuxi 的 7 态（`models_business.py:950-956`）已经涵盖了排队/运行/取消/中断/终态，语义与我们要的一致，改名只会增加与参照实现的对照成本。**新增 `waiting_ingest` 是本项目自研点**——Yuxi 的附件不索引，不存在「等索引」这个挂起源                                                                                                                                                                                                                      |
| **D71** | 审批与索引等待的恢复都走 **checkpointer resume，且产生一个新的 Run**（不复用原 Run 行）；原 Run 以 `interrupted` 终结                                                                                                                | 备选：原地续跑同一个 Run。否决理由：对齐 Yuxi（`agent_run_service.py:167-173,768-769`）——一次 Run 的 attempt 租约、耗时、用量应保持单一语义，跨挂起复用一个 Run 会让「这次运行花了多久」无法回答；新 Run 通过 `parent_run_id` 串联，审计更清晰                                                                                                                                                                                                                                       |
| **D72** | Agent 实体化（`agents` 表：slug / 配置 / 系统提示词 / 工具与 KB 绑定 / 共享）**列为二期**                                                                                                                                            | 备选：一期就做。否决理由：当前只有一个内置 Agent 形态（检索 Agent），实体化的收益要等多 Agent 形态出现（办公 Agent、代码 Agent）才兑现；且它依赖本清单的中间件与工具面先稳定，先做会返工                                                                                                                                                                                                                                                                                             |
