## 1. 背景与目标

### 1.1 背景

检索链路的**算法能力是领先的**——Agentic-RAG（plan/act/grade/rewrite）完整落地，Yuxi 全仓 grep 不到任何 `rewrite`/`decompose`/`grade`；ACL 表达式下推召回内部也是 Yuxi 没有的。

但存在两个**结构性弱点**：

1. **解析与分块 100% 外包给 Knowhere**：`ingest/` 下 `parser/`、`chunking/` 目录已物理删除（`tests/__pycache__` 仍残留 `test_parser`/`test_chunking`/`test_url_validator` 的 `.pyc`）。引擎不可用时路由期 **fail-closed 全停**（`ingest/routing/router.py:93-111`），且分块参数与策略完全不可调。
2. **检索可选空间被收窄**：只有 2 种策略、融合权重不可配、精排锁死 DashScope 单协议，且没有任何质量度量手段（无评估），改动检索策略后无法证明好坏。

### 1.2 目标

1. 给解析链路加**仓内兜底**，把「Knowhere 单点不可用 = 全平台停止摄取」降级为「丢失语义解析增强，但基础 RAG 仍可用」；
2. 补齐检索可调空间（keyword 模式、可配融合、多 rerank 适配器），使检索质量可实验、可优化；
3. 建立**质量度量闭环**（评估体系，二期），让每次检索策略改动都有数字依据；
4. 建立**多跳证据供给**（知识图谱，二期），支撑 agentic RAG 的复杂问句；
5. 补回 URL 摄取（带 SSRF 防护），恢复「从链接建库」能力。

### 1.3 非目标

- **不照搬 Yuxi 的解析器全内置**：7 个 OCR 引擎（含 torch/paddle 重依赖）不进本项目镜像，Knowhere 仍是主路径，仓内只做**纯 CPU 的兜底分块**；
- **不照搬 Yuxi 的 `except Exception: return []`**：本项目分层失败语义（核心上抛 / 可选降级 + `degraded` 标记）更严，保持不变；
- **不引 Neo4j**：图谱优先落在 Milvus（D62），少一个存储与一套运维；
- **不做检索结果重排的 LLM 逐文档打分**（CRAG 式）：判据继续用精排分数这个已有信号，零额外成本。

## 4. 关键决策

| #       | 决策                                                                                                                                                                           | 备选项与否决理由                                                                                                                                                                                                                                         |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D56** | 引入**仓内兜底分块器**：只做 markdown → chunk 的纯 CPU 逻辑，移植 Yuxi 的 RAGFlow-like 6 种 preset；Knowhere 不可用时**降级**而非 fail-closed（响应带 `ingest_degraded` 标记） | 备选：维持 fail-closed。否决理由：把「语义解析增强不可用」放大成「平台不可用」，可用性代价不成比例。备选：仓内也补 OCR。否决理由：torch/paddle 重依赖进镜像 ≈ 数 GB，与本项目「解析外包换部署轻量」的既定取舍冲突（D56 只补分块，不补 OCR）              |
| **D57** | 融合策略参数化为 `fusion_mode: rrf \| weighted`，**默认 `rrf`**（保持现状），`weighted` 走 Milvus `WeightedRanker` 且权重经 KB `query_params` 可配                             | 备选：直接换 `weighted`（对齐 Yuxi 0.7/0.3）。否决理由：RRF 对分数尺度不敏感、无需调参，是更稳的默认；weighted 需要真实评估数据才能定权重，而评估体系要到 D61 才就位。两者并存、默认不变，是零风险演进                                                   |
| **D58** | `SEARCH_MODES` 补 `keyword`，策略注册表加一项                                                                                                                                  | 无实质备选：注册表机制已就位（`strategies/__init__.py:15-18`），「新增模式 = 注册实现，不改编排」是既定设计，属纯增量                                                                                                                                    |
| **D59** | rerank 抽象为多适配器：`BaseReranker` + OpenAI 兼容 / DashScope / 本地 CrossEncoder 三实现，经 `model_factory` 分发                                                            | 备选：维持 DashScope 单协议。否决理由：绑定单一云厂商使自托管部署不可行（与「可私有部署」定位冲突），且换协议要动 `retrieval_service` 内部                                                                                                               |
| **D60** | **推翻 spec D10**，URL 摄取回归，且必须整组移植 SSRF 防护（白名单 + 私网 IP 拦截 + 重定向逐跳复验 + 大小/Content-Type 校验）                                                   | 备选：维持移除。否决理由：spec D10 的移除理由是「以攻击面换功能」，但 Yuxi 那套防护（`url_validator.py:19-71`）是成熟实现，移植成本低于收益；「从链接建库」是知识库的基础入口。**红线：防护与入口同 PR 落地，不允许先上入口后补防护**                    |
| **D61** | 评估体系建为**独立域 `evaluation`**，依赖 `{kb, retrieval, chat, model_provider}`；四表 + P/R/F1@K + LLM Judge。**二期**                                                       | 备选：放进 `retrieval` 域。否决理由：评估要跑 chat 生成（LLM Judge 与答案质量），`retrieval → chat` 是反向依赖，违反现有 DAG；独立域是唯一不破契约的落点                                                                                                 |
| **D62** | 图谱建为**独立域 `graph`**，优先落在 **Milvus**（不引 Neo4j）；`ingest → graph`（建索引）、`retrieval → graph`（图检索）双向被依赖。**二期**                                   | 备选：引 Neo4j（对齐 Yuxi）。否决理由：多一个存储 + 一套运维，而 Yuxi 自身就有 Milvus 内图谱实现（`graphs/milvus_graph_service.py`），说明单存储可行。备选：图谱塞进 `ingest`。否决理由：`retrieval → ingest` 会产生新跨域依赖且方向怪异（检索依赖摄取） |
| **D63** | 检索缓存键 = `sha256(query 归一化 + Scope 指纹 + kb_names + 文档内容指纹集合 + 检索参数)`；缓存 Scope 指纹而非用户 ID                                                       | 备选：按 `user_id` 缓存。否决理由：缓存命中率被用户数稀释，且 ACL 变更后无法定向失效；按 Scope 指纹则 ACL 变更自动换键。备选：不做缓存。否决理由：高频重复问句（FAQ 场景）成本可观，且键设计一旦定错后面难改。**注**：原键含 `active_version`，因 [知识库清单] D52 版本管理缓做（`active_version` 恒 1），改用**文档内容指纹集合**（`documents.sha256`）表达「内容变了缓存即失效」——这正是重摄取后旧缓存必须失效的真实条件 |
