## 1. 背景与目标

### 1.1 背景

知识库域当前已完成**建模 + ACL v2 + 双管线摄取 + 统计**四块，是四个域中最完整的一个。但面向「agentic RAG 平台」目标仍缺两类能力：

1. **产品面缺失**：文档一多即退化为平铺列表（无文件夹）、无法回看历史版本、无法在线预览原文件、无法批量操作；
2. **供给 Agent 缺失**：示例问题与知识导图是 Yuxi 中直接喂给 Agent 的 KB 元数据（`get_mindmap` 工具），本项目完全没有，导致 Agent 拿不到「这个库大致讲什么」的先验。

### 1.2 目标

1. 补齐组织结构能力（文件夹树）与版本能力（历史版本 + 回滚），使知识库在文档量级上升后仍可用；
2. 补齐原文件预览与本库自检入口，降低「入库了但看不出问题」的排查成本；
3. 产出可被 Agent 工具面消费的 KB 元数据（示例问题、导图），为智能体文档中的 `knowledge-base` Skill 备料；
4. 补齐批量操作，消除逐条点击的运维成本。

### 1.3 非目标

- **不做目录级 ACL**（D53）：文件夹仅为组织语义，权限仍在 KB / 文档级，避免与 D47「文档 ACL 只收窄」冲突；
- **不做 KB 类型抽象**（D54）：Dify / Notion / 只读连接器留到有第二个真实后端时再抽；
- **不做软删除 / 回收站**：Yuxi 也没有，属于独立话题；
- **不引入 Yuxi 的 `share_config` 权限模型**：本项目 ACL v2 更强，不制造第二套授权模型。

## 4. 关键决策

> 决策编号续 D51。每条含备选项与否决理由；已落地决策见 `2026-09-12-kb-ownership-and-acl-v2-design.md:408-413`（D45–D50）。

| #       | 决策                                                                                                                     | 备选项与否决理由                                                                                                                                                                                                                                                                                                                                                                    |
| ------- | ------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **D51** | 文件夹使用**独立 `kb_folders` 表** + `documents.folder_id` 外键，**不**照搬 Yuxi 的同表 `parent_id` + `is_folder` 自引用 | 备选：Yuxi 同表方案（`models_knowledge.py:59,73`）。否决理由：① 同表自引用会把「文件夹」塞进 `documents` 的七态状态机与 `active_version`/`sha256` 语义里，产生大量无意义空列；② Yuxi 自己为此背了历史债，需要额外写 `knowledge_folder_service.py:11-71` 做虚拟目录迁移；③ 本项目 `documents.path_prefix` 过滤语义（`kb/crud/crud_document.py:109-111`）已可承载树路径，独立表更契合 |
| **D52** | 版本管理采用「**不可变版本行 + `active_version` 指针**」                                                                 | 备选：历史快照表 / 事件溯源。否决理由：`chunk_id` 主键已编码 `{doc}:{ver}:{idx}`（`kb/model/chunk.py:24-34`），说明版本行形态是既定设计，改形态要动 chunk 主键；指针切换即回滚，无需复制数据                                                                                                                                                                                        |
| **D53** | **不做**目录级 ACL                                                                                                       | 备选：与 ACL v2 对齐增设 `folder` 主体。否决理由：D47 已确立「文档可见集 ⊆ KB 可见集」的单向收窄原则，再插一层文件夹 ACL 会产生三段求值链与新的越权放大面；文件夹只做组织，不做授权                                                                                                                                                                                                 |
| **D54** | KB 类型抽象与只读连接器（Dify/Notion）**列为二期**，一期不做                                                             | 备选：一期直接抽 `KnowledgeBaseFactory`。否决理由：当前只有 Knowhere + PixelRAG 一套实现，YAGNI；但 **KB 表预留 `kb_type` 列的决策随二期走**，一期不加字段                                                                                                                                                                                                                          |
| **D55** | 原文件预览走**独立转换容器**（LibreOffice headless），产物落 MinIO 持久缓存；**不复用 Knowhere**                         | 备选：复用 Knowhere 服务转换。否决理由：Knowhere 是解析服务（重依赖、有摄取限额与队列），把它降级成 Office 转换器会污染其语义边界，且预览是高频读路径、不该排进摄取队列。备选：客户端转换。否决理由：前端不可控、格式覆盖差                                                                                                                                                         |
| **D55.1** | PDF（原生或转换产物）走**服务端 Range 代理端点**，图片走预签名 URL，Markdown/文本走 JSON 内联窗口 | 备选：PDF 也走预签名直连。否决理由：① 预签名 URL 是 bearer 凭据，签发后即绕过 ACL，与 D50「不泄露存在性 + 每请求鉴权」冲突；② PDF.js 一次浏览会话会发几十次 Range 请求，URL 过期即中途 403 断流；③ 预签名路径无法表达「转换未完成」这类业务态。代价：PDF 字节过服务端——但 PDF.js **只取所需字节窗口、不拉全量**，成本可控。图片不代理（单次、小、`<img>` 直用） |
| **D55.2** | Office 转换**默认惰性**（首次预览触发）+ KB 级 `preview_eager` 开关（默认关） | 备选：摄取时预转换。否决理由：LibreOffice 转换是重操作，为没人预览的文档付转换成本不划算；热库可用 KB 开关显式打开。备选：纯手动触发。否决理由：预览是高频交互，要用户点「转换」不可接受 |
| **D55.3** | 转换失败**降级到已入库的 `__parsed__.md`**（Knowhere 产物）→ Markdown 渲染 + `degraded` 标记 | 备选：失败即不可预览（Yuxi 现状，`knowledge/preview.py:101-103`）。否决理由：解析产物本来就在 MinIO（`kb_parsed_object_key`），等于零成本保底；且与项目既有的分层失败语义（核心上抛 / 可选降级 + 标记）一致 |

> **编号说明**：D55.1–D55.3 采用点分子编号。它们同属「预览子系统」这一条主线，用子编号可把改动局限在本文件；若追加为 D79–D81 会在「D51–D55」的文档里出现越界编号，若重排为 D51–D58 则要连带改其余三份文档与全部交叉引用。子编号是这里唯一零 churn 的方案。

### Phase 3 — 预览与批量（D55/D55.1/D55.2/D55.3）

#### 3A. 分级路由（服务端按扩展名判定，**不信任上传的 `Content-Type`**）

| 类别 | 扩展名 | 传输 | 渲染 |
| --- | --- | --- | --- |
| Markdown | `.md/.markdown/.mdx` | JSON 内联（窗口 + 续读游标） | `react-markdown`（前端已有 `^10.1.0`） |
| 图片 | `.png/.jpg/.jpeg/.gif/.bmp/.webp/.svg` | **预签名 URL** | `<img>`；SVG 需 sanitize |
| 纯文本 / 代码 | `.txt/.csv/.log/.json/.yaml/.py/...` | JSON 内联（窗口 + 续读游标） | `<pre>` + 高亮 |
| PDF | `.pdf` | **Range 代理端点** | PDF.js |
| Office | `.docx/.xlsx/.pptx`（+`.odt/.ods/.odp`） | 异步转换 → 转好后走 PDF 路径 | PDF.js |
| 其他 | — | 仅下载 | — |

**为何不信任 `Content-Type`**：`kb/service/document_service.py:60,142` 把客户端提交的 `file.content_type` 直接写进 MinIO，用它路由等于让上传者决定服务端行为。正确做法是上传/摄取时按扩展名白名单算出 `preview_kind` 并**持久化到 `documents`**，`replace_document_file`（`api/v1/documents.py:127`）时重算。

#### 3B. 异步转换链路

```text
GET /documents/{id}/preview
   │ ACL（复用 api/v1/documents.py:31 _require_kb_perm + CurrentScope）
   ├─ preview_kind ∉ office → 按 3A 直接返回
   └─ office → 查 document_previews(document_id, version_id)
        ├─ ready      → 200 { kind: pdf, content_url, page_count }
        ├─ absent     → 落 converting 行（唯一键幂等）→ 入队 kb.preview_convert → 202
        ├─ converting → 202（前端退避轮询）
        └─ failed     → 降级梯（3D）
```

`kb.preview_convert`（Celery，独立队列 `preview`）：**流式**读 MinIO 原文件 → 流式 POST 转换服务 → `soffice --convert-to pdf` → `qpdf --linearize` → `pypdf` 取 `page_count` → 落 `kb/{ns}/{kb}/{doc}/preview/{version_id}.pdf` → 行置 `ready`。

- **幂等**：`document_previews` 在 `(document_id, version_id)` 唯一 + 状态守卫，并发请求不起 N 个任务（同 `job_service.prepare_run:62-66` 桥接写法）
- **`download_document_bytes` 是全量入内存**（`document_storage.py:57-70`），需新增流式读原语，否则大文件转换会打爆 worker

#### 3C. Range 代理端点（D55.1）

`GET|HEAD /documents/{id}/preview/content`：

| 项 | 要求 |
| --- | --- |
| `Range: bytes=start-end` | 返回 `206` + `Content-Range` + `Content-Length` |
| `Accept-Ranges: bytes` | PDF.js 靠它决定是否走分段 |
| `ETag` + `If-Range` | 复用已取窗口 |
| 单次窗口上限 | 8 MiB，避免 `bytes=0-` 一次性拖全量 |
| 数据通路 | MinIO `get_object(Range=...)` 流式转发，不落内存 |
| 任意 offset | **必须支持**：非线性的 PDF 其 xref 在尾部，PDF.js 会先请求文件尾 |

项目目前**无任何 `StreamingResponse` 先例**，这是第一处。

#### 3D. 降级梯（D55.3）

1. Office → PDF 成功 → PDF.js
2. 转换失败 / 超时 / 容器不可用 → **`__parsed__.md`** → Markdown 渲染，响应 `degraded: true` + `fallback_reason`
3. 无解析产物 → 仅下载 + 明确提示

#### 3E. 转换容器加固

| 项 | 做法 |
| --- | --- |
| 镜像与编排 | 按 `docker/knowhere/` 既有约定建独立 compose 项目 `docker/libreoffice/`；`docker-compose.yml` 加注释指路（照 `docker-compose.yml:362-365` 对 Knowhere 的写法） |
| 隔离 | 非 root、`read_only` rootfs、`tmpfs` 放 `/tmp` 与输出、**无出网**、`mem_limit`、`pids_limit`、`cpus` |
| soffice 调用 | **每次转换独立 `-env:UserInstallation=file:///tmp/lo/<uuid>`**（并发共用 profile 会互相锁死）；`--norestore --nolockcheck --nodefault --nologo` |
| 字体 | 装 `fonts-noto-cjk`，否则中文转出来是方格 |
| 超时 | 硬杀 60–120s，超时落 `failed` 走降级 |
| 并发 | 容器内小池（2–4）+ 有界积压，饱和即 `503` 快速失败 |
| 格式 | 白名单 docx/xlsx/pptx(+odt/ods/odp)；**显式拒绝 `.docm/.xlsm/.pptm`**；文件名净化（去路径、禁前导 `-`）、大小上限 |
| 凭据 | 容器**不持有任何 MinIO/DB 凭据**，输入输出均由 Celery 任务流式转发 |

> **xlsx 保真提示**：宽表转 PDF 会按页切列，属固有保真损失。转换时需传 landscape + fit-to-width 的 filter 选项缓解。Yuxi 干脆没把 xlsx 纳入（`utils/filepreview.py:20` 只有 `.docx/.pptx`），本项目纳入并接受该损失。
