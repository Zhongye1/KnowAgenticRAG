## 1. 完整 REST API 端点列表

### 1.1 基础设施（Infrastructure）

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/` | 应用名称、版本、文档链接 |
| `GET` | `/metrics` | Prometheus 指标采集 |
| `GET` | `/health` | Docker / HAProxy 存活探针 |

### 1.2 查询与搜索（Query & Search）

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/query` | 完整 RAG 问答（路由→检索→生成→持久化） |
| `POST` | `/query/stream` | **SSE** 流式问答（step + token 事件） |
| `POST` | `/search` | 纯检索（无 LLM 生成） |
| `POST` | `/search/stream` | **SSE** 流式检索（step + sources 事件） |
| `GET` | `/tags` | 标签目录（用于 Scope Filter UI） |

### 1.3 会话（Sessions）

| 方法 | 路径 | 说明 |
|------|------|------|
| `GET` | `/sessions` | 会话列表（支持 `limit`/`offset`/`kb_name` 筛选） |
| `POST` | `/sessions` | 显式创建会话 |
| `GET` | `/sessions/{session_id}` | 获取单个会话元数据 |
| `PATCH` | `/sessions/{session_id}` | 更新会话标题 |
| `DELETE` | `/sessions/{session_id}` | 级联删除会话及消息 |
| `GET` | `/sessions/{session_id}/messages` | 分页获取会话消息历史 |

### 1.4 文档摄入（Ingest）

| `POST` | `/ingest` | 统一入队入口（文件上传或 URL） |

### 1.5 任务（Tasks）

### 1.13 关键约定速查

- **分页**：列表接口返回 `{ items: [...], limit, offset }`，部分含 `total`
- **删除响应**：`{ "deleted": true }`，重复删除返回 `404`
- **SSE 格式**：`event: <name>\r\ndata: <json>\r\n\r\n`
- **多租户**：`kb_name` 为请求级隔离，`plugin_namespace` 为部署级域隔离
- **认证**：REST 路由默认**无认证**，需部署在内网或网关后

## 2. 落地路线（六阶段）

当前后端仅有 `src/app/admin`（RBAC）与 `src/app/task`（Celery 调度），Milvus / MinIO / MCP / SSE 能力均不存在。按 fba 分层约定（Model → Schema → CRUD → Service → API），分六个阶段依次交付。

### 阶段 0：基础设施层（无 API，一切的前提）

先补依赖和基础封装，不写任何路由：

- **依赖**：pyproject 增加 `pymilvus`、`minio`、`sse-starlette`
- **连接管理**：仿照 `src/database/` 模式新建 `src/database/milvus.py`、`src/database/minio.py`——单例 client，lifespan 里 init/close（挂到 `register_init()`，src/core/register.py）
- **配置**：连接串、bucket 名、MCP 路径统一进 `src/core/config.py`
- **Celery 队列规划**：ingest 管道多队列（parse/embed/index）在 task app 的 celery 配置中预定义

### 阶段 1：领域模型与知识库 CRUD（对应 §1.7 子集）

新建 `src/app/rag/` 目录，按五层结构组织：

```
src/app/rag/
├── model/          # KB、Document、Task 审计、Session、Message、Notification
├── schema/
├── crud/
├── service/
└── api/v1/router.py   # v1 = APIRouter(prefix=FASTAPI_API_V1_PATH)
```

在 `src/app/router.py` 手动挂载 `rag_v1`。本阶段只交付：

- `POST /knowledge_bases` + `GET /knowledge_bases/{kb_name}` —— 一切资源的根
- `GET /health` 扩展版（加入 Milvus/MinIO 连通性检查）

**验收标准**：能创建 KB 并在数据库中查到。

### 阶段 2：文档摄入管道（对应 §1.4 + §1.5）

API 只是薄壳，重活全在 Celery：

- `POST /ingest/validate/*`：纯校验逻辑（大小、PDF 页数、SSRF 防护），同步返回
- `POST /ingest`：文件落 MinIO → 建 Document 行（status=pending）→ 发 Celery 任务 → 返回 job_id。**接口不做解析**
- Task 审计表 + `GET /tasks` / `GET /tasks/{job_id}` 先做轮询版
- 解析→分块→embedding→写 Milvus 的管道在 task app 实现，每步更新审计表进度
- `GET /tasks/{job_id}/stream` 用 Redis Pub/Sub + SSE 包装进度事件（复用已有 `cache_pubsub_manager`）

**验收标准**：上传 PDF → 队列消化 → tasks 接口看到 success。

### 阶段 3：检索与问答（对应 §1.2 + §1.3）

- `POST /search`：Milvus 向量检索 + 标签过滤，纯函数式，最先做
- `GET /tags`：标签目录表或从元数据聚合
- `POST /query`：路由→检索→生成→持久化，Session/Message 表在此落地
- `/query/stream` 与 `/search/stream`：SSE 输出 `step`/`token`/`sources` 事件——LLM 流式输出直接透传，step 事件用统一枚举约定
- Sessions/Messages CRUD 是标准五件套，最后收尾

### 阶段 4：读侧支撑（对应 §1.6 + §1.8 + §1.9）

相对独立，可并行开发：

- Documents 列表/详情/删除。**注意**：KB 级 DELETE 是彻底清空；文档级 DELETE 建议软删 + 后台清理任务，需明确定义级联语义
- Chunk HTML / 图片字节流：`StreamingResponse` 从 MinIO 拉取
- Attachments：独立临时存储目录 + TTL 清理
- Notifications：简单 CRUD + 已读批量操作

### 阶段 5：Admin 与 MCP（对应 §1.10–§1.12）

- `/admin/*` 仪表盘均为只读聚合查询（Redis INFO、Milvus stats、Celery inspect），逐个实现
- 变更类端点（`PATCH /admin/resource-limits` 等）：配置快照存 DB 或 Redis，加审计日志
- `/mcp`：fastmcp Streamable HTTP transport 挂载到指定路径
- SSE 日志流：接 loguru sink 推 Redis Pub/Sub

## 3. 贯穿性决策（先定再写码）

1. **多租户隔离**：`kb_name` 过滤必须下沉到 CRUD 层统一注入，不能靠每个 service 自觉
2. **错误契约**：沿用现有 `errors.NotFoundError` 体系，不自造响应格式
3. **SSE 统一封装**：四个 stream 端点共用一个 helper（心跳、断连清理、事件序列化）
4. **危险操作护栏**：`DELETE /knowledge_bases/{kb_name}` 要求二次确认参数或仅限超管
5. **认证策略**：当前为"网关负责"。若后续接入本系统 JWT，将 admin 的 `DependsJwtAuth` 加到 rag router 即可，但**现在必须决策**，避免返工

每个阶段结束跑一次 lint/typecheck + 手动冒烟。**阶段 2 结束为第一个真正的里程碑（端到端摄入打通）。**
