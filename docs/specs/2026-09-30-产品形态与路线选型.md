## 1. 产品形态定义

### 1.1 一句话形态

> 一个**多租户的知识问答 + 深度调研平台**：客户自助建库、导入文档，在自己站点里嵌一个问答挂件；开发者把同一套能力通过 REST / MCP 接进自己的 Agent；复杂问题由 Agent 跑分钟级调研，产出**可下载的报告产物**。

### 1.2 四个对外面

产品形态由四个面构成，不做「第五个面」的扩张。

| 面           | 使用者           | 现状（2026-09-30 实读）                                                                  | 缺口                                                       |
| ------------ | ---------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **控制台**   | 租户管理员 / 知识运营 | `/app` 下 `chat`、`knowledge`（KB/KG 实，`mcp`/`skills`/`tools` 为「建设中」空壳）、`admin`（用户/角色/部门/KB-ACL） | `overview`、`agents` 为占位页；**无** key 自助管理、来源开关、用量与计费、租户设置 |
| **问答面**   | 终端提问者       | SSE 对话 + `[n]` 引用角标 + Agent 模式开关 + 轨迹面板                                     | 报告产物卡片/下载、断线重连（SSE 无 `id`）                 |
| **嵌入面**   | 客户站点访客     | **零**                                                                                    | 挂件、域名白名单、访客身份、跨域策略                       |
| **集成面**   | 开发者 / 宿主 Agent | MCP 服务端面完整（PAT + scope + 限流 + 审计，5 只读工具）；`/rag/search`、`/chat` 可用      | 客户**自助签发** key 的控制台；公开的 Agent Run API；用量可见 |

### 1.3 对象模型

```text
租户 Tenant ──┬── 成员 / 角色 ── 权限
              ├── 项目 Project ── 工作目录 / 产物 Artifact
              ├── 知识库 KB ── 文档 Document ── 分块 Chunk
              ├── 会话 Thread ── 消息 Message ── Run ── 步骤 / 用量
              ├── 凭证 ApiKey / PAT ── scope
              └── 配额 Quota ── 用量记录 Usage
```

现状映射：`知识库 / 文档 / 分块` 完整；`Run` 仅终态审计（`agent_runs`，status 仅 `ok/empty/error/cancelled`，且只写不读）；**`租户`、`项目`、`产物`、`凭证自助`、`配额/用量` 全为空**。

> ⚠️ **`plugin_namespace` 不能当作租户**：它来自 `PLUGIN_NAMESPACE` + `ALLOW_NAMESPACE_OVERRIDE`（`backend/src/app/kb/utils/namespace.py:13`），语义是「一个实例服务一个命名空间」的部署级开关，不是「一个实例服务 N 个客户」。

### 1.4 三条关键旅程

| 旅程             | 路径                                                                     | 目标       | 断点                                  |
| ---------------- | ------------------------------------------------------------------------ | ---------- | ------------------------------------- |
| **开通上线**     | 注册开通 → 建库 → 传/导入文档（看摄取进度）→ 生成挂件代码 → 贴入客户站点 | < 30 分钟  | 断在第一步（无租户）与最后一步（无挂件） |
| **深度调研**     | 提问 → 判定需长任务 → 子智能体并行（KB + 公网）→ 报告落产物 → 下载/分享   | 分钟级     | 断在长任务容器与工作区                |
| **开发者集成**   | 签 key → 调 `/rag/search` 或接 MCP → 在控制台看用量与审计                 | 自助完成   | 断在 key 自助                         |

### 1.5 计量维度

计量口径**必须先定再开发**（一旦对外就是契约）。候选：文档页数/存储、检索次数、问答 token、Agent Run 步数与时长、报告份数、并发席位。

现状：MCP 端点已有按 `tenant+sub` 分桶的限流（`pyrate_limiter`，`backend/src/app/mcp/api/router.py`），但**无计量落库**，因此当前既不能出账也不能按套餐限流。用量天然挂在 Run 上，应与 ③ 的 Phase 1 同期落地。

### 1.6 非目标（形态边界）

- **不做通用办公 Agent**（明确不追 Yuxi / Mira 的全能形态）：**不引入代码执行沙盒**（D86）、不做 IM Bot 矩阵、不做多端（桌面/插件/移动）；
- 不做 Text-to-SQL、表格问答、推荐系统（来源范围见 D80）；
- 不做 Agent 平权协作（Multi-Agent / Hierarchical），长产物用**子智能体**而非多 Agent 协作；
- 不做完整 ADW（文档批处理/审核流水线）。

## 3. 参照实现对照（Mira × Yuxi）

### 3.1 Mira 的形态

**一句话**：企业级 AI Agent 平台——不是「知识库问答」，而是「一个带沙箱工作台的通用办公 Agent，工具与技能可分发」。

```text
客户端（Web / Electron / Chrome 扩展 / iOS·Android / 飞书 Bot）
   ▼
mira_bff（TS，鉴权 + 路由 + SSE；部分请求直连 server）
   ▼
mira_server（Go，控制面：对话编排 / 项目 / 模型路由 / 技能市场 / 推送 / 灰度）
   ├── mira_harness（Go，数据面：沙箱生命周期 + Agent 编排）
   ├── mira_scheduler（Go，任务调度 + 飞书 Bot）
   ├── mira_search（Go，会话搜索）
   ├── hermes_agent（Go，Claude Code 二开运行时；**与 harness 是同级下游**）
   └── mira_tool_management（Go，Tool/ToolPackage/Skill 元数据 + 市场）
          ▼ MCP Streamable HTTP
      mira_mcp_proxy → mira_mcp_server（21 工具）/ NanoDraw（3 工具）/ 第三方 MCP
```

> ⚠️ Mira 自身 README 的拓扑图把 `harness → hermes` 画成上下游，**实读为同级下游**：`mira_server` 按 `agentName` 分流（`mira_hermes`/`mira_codex` → `/subagent/call`；主 agent → harness `/chat/completions/main_agent`），`mira_harness` 全仓 0 处引用 hermes。

### 3.2 四路实读摘要

| 面               | 关键事实                                                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **控制面 / BFF** | 对象模型 `User ⊃ Project ⊃ Session ⊃ Message`；BFF 已收敛为登录/静态/配置薄层，真实业务面在 `mira_server` 的 `/mira/api/v1`、`/openapi/v1\|acl/v1`（一方）、`/openapi/ext/v1`（三方）三层；**六套鉴权并存**；模型路由 `auto` → 插件灰度（3s 超时）→ 三级降级；**无 BYOK**（平台按用户签发 AK）；Project 三合一（Agent 配置 manifest + 沙箱工作区 + 模板实例），**owner-only、无成员/角色/邀请** |
| **运行时**       | 沙箱可插拔（实际可路由 `bwrap` / `safebox`；`e2b` 有实现但全仓无引用），按 sessionID 划桶 + 灰度路由，失败降级 bwrap；隔离靠 **NAS 路径模板 + 挂载集**；**主对话 SSE 无 seq / 无重放**，只有 A2A 子任务流有 `Last-Event-ID` 重放；Hook 三类（`PreToolUse` / `PostToolUse` / `CanUseTool`） |
| **工具治理**     | 三层元数据：`Tool`（含 `MCPConfig{name,url,headers,auth_types,actions}`）→ `ToolPackage`（有序引用，无 version 字段）→ `Skill`（**独立实体**，zip 必含 `SKILL.md` frontmatter）；Skill 真相源 = TCC + 仓库目录，MySQL 只是缓存；MCP 聚合是**动态**的（header `mira-proxy-tool-ids` → `ListTools(ids)`），凭证按 `auth_types` 转换，工具名 `{server}__{tool}`；上架走 **codebase MR + 邮箱白名单 2 人** |
| **调度 / 搜索**  | 任务三类触发（`TIME/EVENT/MANUAL`，cron 最小 1h）+ **auth→conditions→extractors→actions 四段可配流水线**；**Agent 可通过 MCP 的 8 个工具自助建任务**；推送有多渠道 + **分级脱敏**（私密频道还原、群聊掩码、兜底正则）；搜索是**刻意做浅**的：混合检索但严格单用户、无片段/高亮，返回 SessionItem 列表 |

### 3.4 Mira 的三处「不能学」

1. **不能学它的租户层**——控制面单租户硬编码，多租户改造只在数据面且未收口（safebox metadata 里 tenant 仍硬编码 `"mira"`）。它没有这个问题域的答案。
2. **不能学它的交付/治理方式**——MR 人工审核 + 内部 TCC 当真相源，是内部平台的合理选择，对外 SaaS 不成立。
3. **不能学它的失败处理**——无重试、静默熔断、错误当正常返回；我们的多租户 SLA 承受不起。

### 3.5 Mira × Yuxi 统一借鉴表

**两份参照的性质不同，因而"借什么"也不同：**

| 参照 | 技术栈 | 与 RAG-F 的关系 | 借什么 |
| ---- | ------ | --------------- | ------ |
| **Yuxi**（MIT） | Python + LangGraph/LangChain | **同栈**，可逐行对照 | **代码与协议**：状态机取值、checkpointer 接法、中间件实现、门控逻辑、表结构 |
| **Mira** | Go(Hertz/Kitex) + TS + Python | **异构栈**，无法搬实现 | **形态与治理**：分层元数据、任务域、多租户结构、审批协议、凭证转换、运营流程 |

> Yuxi 的逐条借鉴与移植性标注已在 [③ §6](./2026-09-29-agent-落地改造清单.md) 与 [④ §6](./2026-09-29-skills-mcp-落地改造清单.md)；下表是**两者的交叉视图**，只回答「同一个能力域，两边各怎么做、我们取谁」。Mira 列凡写「快照内未见」者，均受 §0.2 证据边界约束——**不等于它没有**。

| 能力域 | Mira 做法 | Yuxi 做法 | RAG-F 取谁（落点） |
| ------ | --------- | --------- | ------------------ |
| 运行容器与租约 | **快照内无 Run 队列**：harness 靠 Redis `sessionLock`（60min TTL）+ safebox lease 表串行化；子任务取消靠 Redis 轮询 | ARQ worker + PG lease（**投递 vs 事实源分离**）+ 「取租约 → 独立事务续租 → 过期幂等收敛为 failed」 | **取 Yuxi 的语义，不取实现**：Celery（D66）+ 自建 lease/heartbeat（③ Phase 1.7） |
| Run 状态机 | **快照内未见 RunStatus 枚举**（其运行态在控制面别处或未开源） | 7 态 `pending/running/completed/failed/cancel_requested/cancelled/interrupted`（`storage/postgres/models_business.py:950-956`） | **取 Yuxi + 自研 1 态** `waiting_ingest`（③ D70） |
| checkpointer | 快照内未见 | `AsyncPostgresSaver` + 独立连接池（`storage/postgres/manager.py:295-324`） | **取 Yuxi**（③ D64） |

| 技能包规范 | zip + `SKILL.md` frontmatter + ToolPackage 分层 | `SKILL.md` 中心 + 差量复制投影 | **取 Mira 的包规范 + Yuxi 的渐进式披露**；投影两边都不取（D86） |
| 技能治理 | **运营制**：codebase MR + 邮箱白名单 2 人 | 用户自装 + 内置同步 | **都不取**（Mira 侧为反模式）：改为自助 + 审核状态机 + 用户级授权 |
| 工具门控 | 动态工具中间件 + ToolPackage 下发 | **注册与可见性解耦**（Yuxi 自己标注"不可省略"） | **取 Yuxi**（D74/D76/D78） |
| MCP 消费端 | 聚合 + `auth_types` 凭证转换 + `{server}__{tool}` | 仅 `sse`/`streamable_http`，**禁 stdio** | **两者都取**：Mira 的凭证转换 + Yuxi 的 transport 白名单（D77） |
| 沙盒 | 三后端可插拔 + 挂载集 + Pause/Resume | 远程 `sandbox-provisioner` + 无凭据执行 | **都不取**（D86） |

| 多租户 | `Tenant`/`Registry`/`Capability`（仅数据面，控制面单租户） | 无 | **都不可搬**，自研（D79/D86） |

| 反模式 | MR 上架、无重试、错误当正常返回、控制面单租户硬编码 | 附件不进索引、`TodoListMiddleware`、ARQ、沙盒供应商路径 | 已分别列入 §3.3 与 ③④ 的「反模式」档 |

**3.5.1 两边一致的强信号（照做，不必再论证）**

`SKILL.md` 中心化 · 工具元数据与可见性门控 · 切面体系（Mira 的 Processor/Hook ↔ Yuxi 的 Middleware）· 子智能体 + 线程归属 · 产物实体化（带权限）· 会话/消息服务端持久化 · **模型 spec 与网关收敛**。

**3.5.2 只有 Yuxi 有、但我们必须自建（Mira 快照内未见）**

Run 状态机 · attempt 归属表 · FIFO 队头派发 · 租约/心跳/取消 · Postgres checkpointer —— **[③ 清单](./2026-09-29-agent-落地改造清单.md) 的运行时部分实际上单一参照 Yuxi**，Mira 在这块没有可借鉴物（它的运行态在其控制面别处或未开源）。这条同时解释了为什么 ③ 的 D64–D71 全以 Yuxi 为参照。

**3.5.3 两边冲突时的取舍**

| 冲突点 | Mira | Yuxi | 我们的选择 | 依据 |
| ------ | ---- | ---- | ---------- | ---- |
| 队列实现 | ARQ | ARQ | **Celery** | D66：仓库已有 RabbitMQ + Celery 全套运维面 |
| 技能落地形态 | bind-mount 投影 | 差量复制投影 | **都不投影** | D86：两者都以「存在可读写文件系统」为前提 |
| 审批配置 | 模式化 + 协议化 | 工具名硬编码 | **协议化** | 工具集会随 MCP 接入变化，硬编码必然过期 |
| 技能上架 | MR 人工审核 | 用户自装 | **自助 + 审核状态机** | 对外 SaaS 不能要求客户提 MR |

**3.5.4 一句话分工**

> **从 Yuxi 借代码与协议，从 Mira 借形态与治理。**

## 4. 路线对比

### 4.1 三个方案

**方案 A — 窄路由器增量**：仅在现有图上加 `web_search` 工具、`plan` 扩来源、MCP 客户端接入；保留 HTTP 直跑 + 180s 墙钟。
→ 1–2 周可见三源闭环；**做不了分钟级报告**（撞墙钟、断线即丢）。

**方案 B — ③ 清单原样全量**：严格按 Phase 0 → 1 → 2 → 3 顺序落地（**D86 后 Phase 0 已收敛为产物服务**，沙盒不在任何方案内）。
→ 上限最高；但最慢，且把产物服务、运行态、挂起恢复**串行**做完才谈商业化，期间租户层零进展、不能对外开通客户。

**方案 C — 商业化前置 + 运行态先行，沙盒拆分延后**（推荐）：

- **第 1 段（可售卖闭环）**：租户层（实体 + 成员角色 + 配额计量 + key 自助 + 挂件）与 ③ **Phase 1**（Run 状态机 + `agent` 队列 + `/runs` API）**并行**；
- **第 2 段**：③ **Phase 0 收敛为产物服务 0a**（PG 行 + MinIO 对象 + 版本 + preview），原 **0b（沙盒执行器）依 D86 直接删除**；同期做 ③ Phase 3.6 工具注册表 + 窄路由器三来源 + ③ Phase 3.8 子智能体；
- **第 3 段**：③ Phase 2（checkpointer / interrupt / 审批）+ 3.7 完成 + 4.4 服务端会话持久化。

### 4.2 对比

| 维度                     | A                | B                | **C（推荐）**      |
| ------------------------ | ---------------- | ---------------- | ------------------ |
| 能否对外开通客户         | ❌ 无租户层      | ❌ 期间无租户层  | ✅ 第 1 段         |
| 分钟级长产物             | ❌ 撞 180s 墙钟  | ✅               | ✅（第 2 段起）    |
| 三源路由（KB/Web/MCP）   | ✅（最关键能力） | ✅               | ✅（第 2 段）      |
| 对 ③ Phase 0 的处理      | 不做             | 全量先做（0a + 1 + 2 串行） | **只做 0a**（D86）   |
| 交付周期                 | 1–2 周（验证级） | 最长             | 分段可交付         |
| 对 ③ 既有结论的改动      | 大幅削减        | 无               | **仅重排顺序**     |

### 4.3 推荐理由（一句话）

**交付物是文本型长产物，不是代码产物**——沙盒对它是超配（③ 把 Phase 0 当硬前置，前提是「技能」；报告不需要）；而**租户层才是真正的阻塞项**：一天不做，一天不能对外开通。

## 8. 里程碑与验收

- **M-A｜租户开通闭环**：新客户自助注册 → 建库 → 上传 → 问答 → 拿挂件代码贴入站点（< 30 分钟）。
- **M-B｜长任务闭环**：提交 Run → Celery 执行 → SSE 全程可观测 → 产物可下载（含断线重连不丢帧）。
- **M-C｜三源路由**：KB / 公网搜索 / MCP 工具三类来源可选，且**未开通的来源对模型不可见**（能力快照门控生效）。
- **M-D｜计量可查**：用量按租户与密钥聚合，可出账、可按套餐限流。
