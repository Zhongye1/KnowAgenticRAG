## 1. 总体拓扑

开发模式**依赖跑容器、代码跑宿主机**，统一从 `Taskfile.yml` 入口操作（`task dev` 一键起前后端）；部署形态见 §7。

```text
  浏览器
    │ REST / SSE / WebSocket(/ws)
    ▼
  React 19 + Vite 前端（dev :5000；OpenAPI 生成客户端调后端）
    │
    ▼
  FastAPI 后端 ragf_server（:8000，fba 模板，uvicorn 热重载）
  ├─ 业务域：admin · kb · ingest · retrieval · chat · model_provider · task · mcp
  └─ 横切：中间件链（日志→请求状态→CORS→i18n→限流→JWT）· OTel 全链路埋点
    │            │            │           │            │
    ▼            ▼            ▼           ▼            ▼
 PostgreSQL16  Redis      RabbitMQ     Milvus 2.5    MinIO
 （事实源）  （缓存/吊销） （broker）  （+etcd）    （对象存储）
    ▲                         ▲
    │ result backend          │ 消费（三队列独立路由）
  Celery：ragf_celery_worker / ragf_celery_ingest_worker
          / beat（定时对账） / flower / exporter
    │ HTTP :5005
    ▼
  Knowhere 解析栈（docker/knowhere/ 独立 compose：app + postgres + redis + localstack，
  内部 MinerU 语义解析；凭据 DASHSCOPE_API_KEY 等在其独立 .env）

  可观测栈（deploy/backend/grafana/）：Loki · Prometheus · Grafana Alloy · Tempo
  ← 后端 OTel（FastAPI/SQLAlchemy/Redis/httpx/Celery/openai 自动埋点）
```

## 2. 后端：业务域与依赖方向

域内五层 `api（薄路由）→ service（编排）→ crud → model（ORM）→ utils`，kb / model_provider 为完整五层，retrieval / chat / mcp 为 api → service 两层。**8 个业务域互不依赖**，域间方向由 import-linter 强制（`backend/pyproject.toml [tool.importlinter]`，违规阻断提交）：

```text
mcp ──→ chat ──→ retrieval ──→ kb
 │        │         │
 └────────┴──→ model_provider ←── ingest ──→ kb / task
```

| 域              | 职责                                                                                     | 依赖约束（决策号）                                          |
| --------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `admin`         | JWT / RBAC / 用户·角色·菜单·日志                                                          | 被横切层反向豁免的已知债务（`common.security → admin`，待下沉） |
| `kb`            | 知识库/文档/分块/ACL/标签 CRUD，租户 scope 依赖注入（`kb/deps.py`），chunks 事实源         | 基础域，不依赖其他业务域                                     |
| `ingest`        | 上传/URL 入队、双管线解析、分块、向量写入、限额、对账                                     | 只消费 kb 只读契约（D9）+ model_provider 客户端；任务派发走 `app/task`（D10） |
| `retrieval`     | 同步检索门面：策略召回 → RRF → 精排 → 来源补全（详见 [检索与问答设计](../RAG_core/02_检索与问答设计.md)） | 依赖 kb、model_provider                                      |
| `chat`          | SSE 流式问答、引用组装、prompt 上下文                                                     | 复用 retrieval 门面（D18），不直连 Milvus                    |
| `mcp`           | MCP 工具面：列库 / 检索 / 带引用问答 / 读片段（PAT 鉴权）                                 | 只编排 chat/retrieval/kb 服务门面，**不直连存储**（D30）     |
| `model_provider`| 模型工厂（embed/chat/rerank/visual 编码）+ ModelCache + 连通性测试；OpenAI 兼容协议 + DashScope | 基础域；模型 spec 形如 `provider:model`                      |
| `task`          | Celery 实例与队列划分（默认 + ingest/knowhere/visual 独立队列）、动态定时 DatabaseScheduler | 任务代码域内归属（D10）                                      |

`common/`（security/cache/exception/response/observability…）、`database/`（db/redis/milvus/minio 客户端）、`middleware/` 是被所有域依赖的横切层，禁止反向依赖业务域。

## 3. 数据面：存储职责与一致性

**核心原则：PostgreSQL 是唯一事实源，Milvus / MinIO 是可重建的镜像。** 所有对账、审计、补偿都以此为基准。

| 存储         | 角色             | 内容                                                                                     |
| ------------ | ---------------- | ---------------------------------------------------------------------------------------- |
| PostgreSQL16 | **事实源**       | 业务元数据、`documents`/`chunks`（正文）、`ingest_jobs`（job 级审计）、`document_keywords`/dedup、`rag_kb_acl`、sys_* |
| Milvus 2.5   | 检索镜像         | `ragf_text_{dim}`（dense + BM25 Function + ACL 标量）、`ragf_visual`（2048d 视觉向量 + ACL）；租户经 namespace → Database 分库 + 分区键 |
| MinIO        | 对象存储         | 原始文件（`kb/{ns}/…` 对象键）、解析产物、视觉管线 tiles 图                                |
| Redis        | 缓存与状态       | 缓存装饰器、JWT 吊销名单、model_provider ModelCache、pubsub                                |
| RabbitMQ     | 任务 broker      | Celery 默认队列 + ingest/knowhere/visual 独立队列（可独立路由与并发）                      |

**写入一致性（摄取侧）**：先写 Milvus 向量、后写 PG chunks 的双写顺序，PG 失败时删 Milvus 向量补偿；`ingest.reconcile` 由 beat 周期对账（声明值 vs PG vs Milvus，以 PG 为准，覆盖视觉管线）。**读侧**：检索命中的正文/文件名/token 一律回查 PG 补全，Milvus 只出 ID 与分数（见检索设计 §9）。

**模型侧一致性**：查询侧 embedding 缺省兜底与摄取侧同源（千问平台），防止两侧向量空间错配；`ragf_visual` 集合带编码器指纹，指纹不一致且非空时拒绝重建。

## 4. 关键链路

### 4.1 摄取（Celery 异步，双管线）

上传/URL 端点 `send_task` 入队（ingest/knowhere/visual 三队列）→ `ingest.tasks.tasks: ingest.process_document` **路由入口**：策略链（前缀强制 → URL → PDF 形态探测 → 扩展名，默认 auto）决定管线——

- **knowhere 管线**：pdf/docx/pptx/md/txt/csv → Knowhere SDK（:5005）语义解析，产出 chunks + doc_nav + 关键词 → 千问文本向量（1024d）；
- **visual 管线**：png/jpg/扫描件 → PixelRAG 渲染切片 → qwen3-vl-embedding 视觉向量（2048d）→ tiles 落 MinIO；
- 引擎不可用时**路由期 fail-closed 报错**（legacy 工厂链已删除）；共享：限额三道关（`ingest/limits.py`，200MiB / 200 页等）、dedup 成功后置登记（D9）、`ingest_jobs` 细粒度审计（job_id = Celery task_id）。

详见 [双管线摄取设计 spec](../specs/2026-09-10-dual-pipeline-ingest-design.md) 与 [双管线摄取架构流程图](./双管线摄取架构流程图.md)。

### 4.2 检索与问答（同步只读 + SSE 流式）

`KB 归属/ACL 校验 → embedding → 策略召回（hybrid：dense+BM25 服务端 RRF(60)；可选视觉召回 ragf_visual，独立 visual_results 返回）→ CrossEncoder 精排（失败降级）→ PG 来源补全 → 引用组装 → chat 模型流式输出`。SSE 事件协议（meta/citation/delta/usage/done/error）、参数三层合并、ACL 三层下推的完整展开见 [检索与问答设计](../RAG_core/02_检索与问答设计.md)。

### 4.3 MCP 工具面（Agent 接入）

PAT 鉴权 + scope 授权（`rag:kb:list/search/read/chat`）+ 限流 + 调用审计（`mcp_call_log`），暴露四个只读工具：`list_knowledge_bases / search_knowledge / answer_with_citations / read_document_chunks`。工具只编排 chat/retrieval/kb 门面，不直连存储（D30），使 Codex / Claude Code 等宿主 Agent 可自主完成「列库 → 检索 → 读片段 → 带引用回答」闭环。详见 [Agent 接入与问答闭环设计](../specs/2026-09-05-agent-layer-and-mcp-design.md)。

## 5. 横切机制

| 机制     | 设计                                                                                                                                          |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 多租户   | 两轴隔离：实例域 `plugin_namespace`（PG 行级 + Milvus Database 分库 + 分区键）× 知识库 `kb_name`（Milvus 标量过滤，由 `milvus_kb_ops` 统一注入） |
| 认证授权 | JWT 中间件 + 路由权限装饰器（`RequestPermission` + RBAC）；检索侧 ACL 以 Scope 三层下推（租户 → KB 级 → 文档级），过滤在召回内部由服务端构造 |
| 配置     | 全部走 `core/config.py` Settings（pydantic-settings），RAGF 业务参数 `RAGF_` 前缀集中声明；插件配置经 `plugin/settings_source.py` 并入          |
| 可观测   | OTel 全链路（trace + metrics）→ Tempo/Prometheus，日志 → Loki；指标只打域门面与外部依赖边界                                                    |
| 异常     | fba 统一异常体系（`common/exception`）；SSE 场景语义错误统一转 `error` 事件（code + msg + trace_id）                                           |
| 流式     | sse-starlette `EventSourceResponse`；实时通道 python-socketio 挂 `/ws`                                                                          |

## 6. 前后端契约：OpenAPI 代码生成

接口类型不手写：后端 FastAPI 导出 `/openapi` → `frontend/scripts/generate-api.mjs` 生成 `frontend/src/generated/`（每端点 = axios 函数 + queryOptions + React Query hook）。Schema 字段的 `Field(description=...)` 是文档来源，前端生成物直接依赖它。改动后端接口后：起后端 → `pnpm generate:api`。前端分层与 feature 边界由 dependency-cruiser 强制，设计令牌有 `check:tokens` 守护。

## 7. 部署形态（docker-compose）

| 组       | 服务                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 开发依赖 | `ragf_postgres` `ragf_redis` `ragf_rabbitmq` `ragf_minio` `ragf_milvus`（含 etcd）                                                          |
| 应用     | `ragf_server`（FastAPI）、`ragf_nginx`（部署入口）、`ragf_ui`（占位，前端暂不进容器）                                                       |
| Celery   | `ragf_celery_worker`、`ragf_celery_ingest_worker`（ingest 独立队列）、`ragf_celery_beat`、`ragf_celery_flower`、`ragf_celery_exporter`     |
| 可观测   | Loki、Prometheus、Grafana Alloy、Tempo                                                                                                     |
| 独立栈   | `docker/knowhere/`（解析服务 app + 专用 postgres/redis/localstack，随 `deps-up` 拉起，可 `task knowhere:*` 单独运维）                        |

镜像由 `Dockerfile` 构建（`ragf_server` / `ragf_celery_*`，`task docker-build`）；根 `.env` 只供 Compose（容器账号与端口映射），后端运行时读 `backend/src/.env`（`task env:check` 校验两层一致性）。

## 8. 工程守护：三层「架构即代码」

1. **提交时**：pre-commit 通用钩子（ruff、tombi、uv-lock…）+ 两个本地架构钩子——backend `import-linter`、frontend `dependency-cruiser`，**违规直接阻断提交**；豁免必须在配置文件显式声明并注明决策依据。
2. **CI 时**：`architecture.yml` 复跑两端架构契约（main 与 `refactor/**`）。
3. **运行前**：前端 `check:tokens` + `check-types`；后端 `pyright` + `pytest`。
